## Boundary decision

**Already done (reject as a novelty claim):**
- Independent re-execution of an agent's work against an exact source state, in a sandbox, with a signed attestation and an accept/incomplete outcome (FalseGreen, commercial). **"We replay the agent's tests independently" is a crowded claim.**
- Replay of tool calls with an UNVERIFIED state (Belay `[snippet]`); sandbox re-verification (Nom Army, via the survey).
- Evidence-gated autonomous lifecycle control (Proof-or-Stop; Jarmak), trust or autonomy tiers enforced by an external policy engine (AWS pattern, Bhati, ActPlane), signed provenance for agent changes (in-toto / SLSA proposals).
- Measuring that agent descriptions disagree with the diff (Gong et al.).

**Potential gap requiring further verification** (all narrow; none established):
1. **A deterministic, per-statement audit of the claims in the agent's closing report, by kind, with measured per-kind precision, an explicit UNKNOWN, and withdrawal of kinds that fail their threshold** (our stage 1 and 2 studies). The found systems verify criteria the agent defined up front (FalseGreen), trace-level state (Belay), or lifecycle gates (Proof-or-Stop); Gong et al. measure description inconsistency but no tool that audits statements by kind was found. Verification needed: a wider search of tools that parse and check PR-description claims.
2. **Comparing evidence from the agent's captured execution context with evidence rebuilt from the project's declared setup**, with provenance (`capture_authenticated`, `partial_replay`, `harness_warning`) as record fields. No found work does this (FalseGreen builds its own environment). Our evidence is small and Python-only (E3 feasibility; run 2 found no decision value beyond reproducibility).
3. **Positioning rather than novelty:** local-first, open core, no hosted execution of customer code, honest negative results. FalseGreen is hosted and paid; Proof-or-Stop is self-hosted with local keys.

## Consequences for an automated consumer
1. **Nothing here is a research contribution.** An acting policy that reads the evidence record is engineering on top of existing ideas (Proof-or-Stop, Cedar-style policy, AWS tiers); it is labelled so and no novelty is claimed.
2. **The product statement "independent test verification" is crowded and, on our own evidence, weakest** (stage 2: all test claims UNKNOWN). This agrees with not anchoring the product on test replay.
3. **The shadow-mode experiment must carry baselines**: CI only; agent-produced local receipts (Proof-or-Stop style); a cheap text detector for false success (Advani's TF-IDF result); and, if obtainable, an independent acceptance replay (FalseGreen-style). It should be able to say whether the record adds anything over these at what cost, and it must measure gate strength with seeded faults, since "zero breakage often means a weak gate".
4. **The real-work "green-but-wrong" base rate is an open problem for everyone** (named as missing by Proof-or-Stop); an honest design reports it with the denominator.
5. **Attestation format:** if the record is made portable, an in-toto statement with a custom predicate is the existing route; the supplied-capture caveat (unauthenticated origin) must stay explicit.
