# TypeScript API diff: documentation read and no-build prototype (2026-11-01)

Step 1 of `API_DIFF_TOOLS_SURVEY.md`. **Exploratory; not pre-registered; precision not measured against independent ground truth; not integrated into the package.** Prototype `research/ts_apidiff/exports.js` and `run.py`; raw output `docs/research/apidiff_bakeoff_data/ts_bakeoff.json`.

## What the primary documentation says `[read]`
Pages read: api-extractor.com landing, overview, "invoking", "configure API report", the `api-extractor.json` reference, and the README of `@clerk/break-check`. Not read: break-check's source, the `run` command page, the message reference.
- `@microsoft/api-extractor` 7.60.1 is **MIT** (checked in the repository's `LICENSE` and `package.json`); `typescript` is Apache-2.0.
- **It needs a built `.d.ts` entry point, not source** ("TypeScript source files are not directly analyzed"), so the project must be compiled first with `declaration: true`. A missing or broken `.d.ts` is not described on the pages read.
- **It does not classify breaking changes.** It writes an API report (`.api.md`) and fails a production build when the regenerated report differs from the committed one; breaking changes are found by diffing that report in git.
- Whether it runs project code (plugins, scripts) is **not stated** on the pages read; building the project with `tsc` does run the project's toolchain.
- `@clerk/break-check` (MIT, 3 stars) wraps it: snapshots the public `.d.ts` surface of a baseline and the current state (it needs both built, via git worktrees or a stored snapshot) and classifies changes by documented rules (removed export or member, required parameter added, optional made required, parameter or property type changed, modifier changes: breaking; optional additions: non-breaking). Limits it states: generics are compared as text, any type change counts as breaking, subpaths it cannot process are skipped with a warning.

## Consequence for Agentvow
The full-fidelity route needs the pull request's project to **build** in the sandbox (dependencies installed, `tsc` run), which is the same hard step that leaves a third of Python pull requests unscorable, and which executes repository tooling. A no-build route can still catch the clearest breaks syntactically, as the Python check does.

## The prototype
`exports.js` parses one TypeScript file at two versions with the TypeScript parser alone (no type checking, no resolution, nothing installed from or run from the repository) and reports **breaking** (removed export or member, parameter removed, required parameter added, optional made required, rest-ness changed, property made required or readonly; rules taken from break-check's documentation) and **changed** (declared type text differs, reported separately because only text is compared), with wildcard re-exports and parse errors listed as gaps.

## Measurement (same method as the Python bake-off)
The 360 pull requests with a backward-compatibility claim that change no Python file; 135 have non-test `.ts`/`.tsx` files that existed at the base commit (576 files; the rest change only tests, `.d.ts`, JavaScript or non-code). **19 of 135 (14%) have a breaking finding**, 18 more only a type-text change, 12 have gaps (wildcard re-exports or parse errors). For comparison the Python tools flag 19% (28 of 149).
Findings: 79 removed names, 14 removed files, 5 parameter changes, 2 properties made required, 1 kind change.

**Is a flagged file a public API?** The main weakness. For the 19 flagged pull requests I looked up the nearest `package.json` at the head commit: **8 are in packages marked `private`** (applications, not libraries: no public API exists), 1 in a package with no entry field, and 11 in packages that declare an entry (`main`, `types`, `exports` or `module`). A declared entry does not mean the changed module is reachable from it: for example a removed helper in a rulesync utility file or in an Obsidian plugin's internals is internal, and the plugin `main` is a bundle, not an API. So at most about 11 of 19, probably fewer, concern a public surface; the true count is not established. I read file lists, not the code of each case, so I make **no precision claim**.

## Decision
- The syntactic diff finds removals and signature changes without a build, but **without entry-point resolution it cannot say which names are public**, so used as-is it would over-flag application code and internal modules.
- Needed before integration: (1) a package filter: a change confined to `private` packages gets UNKNOWN ("no public API declared"), not a finding; (2) reachability from the declared entry through the entry file's re-exports, syntactically; (3) a second look at the remaining flagged pull requests by reading the code, with the result reported as agreement with my reading, not as independent verification.
- Keep the break-check/api-extractor route as the higher-fidelity option for packages that build in the sandbox; do not depend on break-check (3 stars, young).
- Nothing was added to the Agentvow package; no release is needed.

## Revision (2026-11-01, same day): false findings fixed, public-surface filter added
Reading flagged code found two kinds of false finding, both fixed in `exports.js` and rerun on the same 135 pull requests:
1. **Unparseable file.** In mastra 6084 the head version of `stores/clickhouse/src/storage/index.ts` does not parse from line 314 (146 parser errors) and the prototype still reported 26 "removed" members from the half-parsed tree. **A parse error on either side now gives a gap and no findings.**
2. **Inherited members.** In dot-ai 50 the members of `PatternSearchOptions` moved to a base interface (`extends BaseSearchOptions`), so they are still available. **A removal under a class or interface whose base types changed is now reported as "changed (may be inherited)", not breaking.** Removed parameters are now listed by name, not position.

A public-surface filter (`research/ts_apidiff/reach.py`) then classifies each flagged file by the nearest `package.json` at the head commit and a syntactic walk of re-export declarations from the package's source entry (types/main/exports mapped from a build folder to `src/`, else `src/index.ts`): **private** (a `private` package has no public API), **no entry found**, **unreachable** (not re-exported from the entry), **reachable**. File-level only: a reachable file may keep some names internal.

**Result.** Breaking findings: **15 of 135 pull requests** (was 19), plus 12 whose only result is a gap. Among the 15: 6 private packages, 2 with no entry found (rulesync, a command-line tool), 4 unreachable from the entry, **3 reachable**. I read the code of the 3: MetaMask 6307 (the `openSeaApiKey` option and `setApiKey` of a controller exported from `@metamask/assets-controllers` removed) and inbound 57 (the `emailAddress` alias of the SDK client removed) are removals of public members; ion2-calendar 357 changes a component constructor's parameters, a real signature change but one that matters little where the class is built by Angular's injector. **That is about 2 clear public breaks in 135 pull requests; the count is too small to estimate a precision or a recall, there was one reader (me), and the 4 "unreachable" and 2 "no entry" pull requests were not read.** Whether the claims were actually false (MetaMask's claim concerns a different flag; inbound says it "kept backward-compatible aliases") was not adjudicated.

**Updated decision.** The syntactic route plus the public-surface filter removes most noise (13 of 19 originally flagged pull requests are now explained as private, unparseable, inherited or not reachable), but it fires on about 2% of TypeScript pull requests, so it is a narrow signal. Next if continued: integrate as an optional Node-based engine (returns UNKNOWN for private or entry-less packages and for parse errors), and compare against `break-check` on packages that build, to see what the no-build route misses. Not integrated into the Python package.

## Precision work after release 0.5.0 (2026-11-03)
Two refinements in the shipped engine (`agentvow/ts_api.py`, `agentvow/ts/reexports.js`): (1) **name-level reachability**: a name-limited re-export (`export { a } from "./x"`, `import { a } ...; export { a }`) makes only `a` public in `x`, `export *` passes on what is public in the re-exporting file, and findings about other names are reported as "not re-exported" instead of as breaks; (2) **every `exports` subpath** of `package.json` is an entry, not only the root (data, styles and binaries are dropped). A wildcard re-export is now a gap only when it changed (before, every `export *` in an entry made the result UNKNOWN). 6 new tests (14 in the file).
**Check on real code.** The engine was run on shallow, fetch-only clones (no install, no scripts) of the 15 flagged pull requests above: it returned the **same 3 public-API findings** (MetaMask `openSeaApiKey` and `setApiKey`, inbound `emailAddress`, ion2-calendar constructor parameters) and explained the other 12 (7 private package, 3 not re-exported from the entry, 2 no source entry found). **None of the 15 outcomes changed**, so these refinements are correctness work and show no measured gain on this data; the 120 pull requests that were not flagged were not re-run, so any new finding there (a subpath that used to be missed) is not counted. Recall against real breaking changes remains unmeasured. Data: `docs/research/apidiff_bakeoff_data/ts_validate_clone.json`; script `research/ts_apidiff/validate_clone.py`.

## JavaScript (2026-11-03)
The engine now also reads `.js`, `.jsx` and `.mjs` (compiled output, bundles and configuration files are excluded; `package.json` entries may name source files directly; CommonJS is a gap). Of the 360 non-Python pull requests with a backward-compatibility claim, **22** have non-test JavaScript source files (115 files). Findings: **1 pull request flagged** (an application server, `siteboon/claudecodeui` 157; the shipped engine on a real clone correctly says it is not re-exported from a package entry) and 6 with only gaps: 8 files are **CommonJS** (not compared) and 4 sides do not parse (JSX or Flow syntax in `.js`). **No public-API change was found in JavaScript.** The largest limiter is CommonJS; comparing `module.exports` objects would reach about 6 more pull requests (under 2% of the 360), so it was not built. Data: `docs/research/apidiff_bakeoff_data/ts_bakeoff_js.json` and `validate_clone_js.json`.
