# Mutation study: does mutation testing add information beyond changed-line coverage? Pre-registration (written 2026-10-14, BEFORE any mutant is generated or run)

Status: **plan only, nothing run.** Follows `MUTATION_VS_COVERAGE_PLAN.md` section 6, whose decision was "investigate further" (21 planted mutants: 2 survivors on executed lines, S/R = 12.5%; only 10 of the 21 were valid code-changing mutants; a ceiling of 8 comparable cases). This study is the larger test that result asked for. It is an experiment about the **value of the evidence**, not a commitment to build mutation testing into Agentvow. No agent runs, no spending (compute only), no Jev, no learned planner.

## 1. Question and estimand
Among changed executable lines of agent-authored changes that the claimed tests **execute**, how often does a **valid** mutant of that line survive those tests, and are the survivors meaningful test gaps rather than equivalent mutants? "Information beyond coverage" = survivors on executed lines (coverage reports those lines as covered; only mutation shows that the tests do not distinguish them), against survivors on unexecuted lines (coverage already shows the gap).

## 2. Population (fixed now; amended 2026-10-14 by owner decision, before any registered mutant is run: see the deviation log)
The **valid runs of Stages B3, B4, B5 and B6** (`STAGE_B3..B6_RESULTS.md`; valid = the agent's target tests pass in its environment and fail on the baseline: 11 + 8 + 18 + 22 = 59 runs). The original plan used the 22 B6 runs only. **Included:** runs that can be rebuilt from the saved patch (no untracked files missing from it) and whose patch adds at least one non-test Python line the tool can mutate. **Counted before the amendment (enumeration only, no test run, no outcome read):** 53 rebuildable runs (B3 11, B4 6, B5 18, B6 18) with 784 candidate mutants on 1,032 added lines; **46 runs and 29 repositories have at least one candidate; 7 have none**; after the cap of 25 per run the sampling frame is **502 candidate mutants**. **Excluded and reported:** the 6 valid runs that created untracked files not present in the saved patch (B4 2, B6 4). Results are reported per stage and pooled; the environment is rebuilt for every run by the same fuller-capture rule regardless of stage, so the stages' different capture designs do not enter. The suite under test is the run's **claimed target tests** (the tests the agent's claim is about); a secondary check uses the project's full suite (section 4).

## 3. Procedure (fixed now)
1. **Environment.** For each run, rebuild the head state (base + target tests + saved patch) and build the clean environment from the captured package list exactly as B6's capture context (fuller capture, `AGENTVOW_MAX_ENV_MB=3072`), run the target tests twice; **a run whose target tests do not pass twice is excluded as flaky** (listed). Mutation tooling lives in a **separate** virtual environment so the captured environment is not altered.
2. **Coverage.** Run the target tests once under `coverage` (empty rc file) to know which changed executable lines they execute.
3. **Mutants.** Generated by an existing, maintained tool rather than by our own operators: **cosmic-ray 8.7.0** (PyPI, last upload 2026-08-09, requires Python >= 3.9) with its default operator set. Candidates are restricted to **lines the agent's patch added or modified in non-test Python files**, must **parse** (the tool's "incompetent"/invalid mutants are excluded and counted), and are sampled **at most 25 per run**, uniformly at random with a fixed seed (20261015), stratified by operator family so one operator cannot dominate. `mutmut` was considered and rejected because its whole-project trampoline design does not restrict to changed lines; `mutatest` because it has not been released since 2022. **Tool-validity step (not part of the data):** before the registered pass the pipeline is tried once on the smallest rebuildable run to confirm that line restriction, restoration of the file after each mutant, and sandboxed test execution work; its results are discarded and any fix is logged in the deviation log below.
4. **Execution.** Each mutant runs the target tests in the **same platform sandbox** as every Agentvow replay (the tool's test command is wrapped; if the wrapper cannot be made to work for the tool, that is a logged deviation and the affected run set is reported), in a disposable worktree copy, one mutant at a time, with timeout = max(10 s, 5 x the run's baseline test time). Outcomes: **killed** (target tests fail or error), **survived**, **timeout** (counted as killed in the primary rate, also reported separately), **incompetent** (excluded). Wall-clock cap: 20 minutes per run and **8 hours in total** (raised from 4 by the amendment for the larger population); a run that hits its cap is reported with the mutants completed.
5. **Join.** Every mutant is labelled executed or not executed by the coverage of step 2.

## 4. Review and secondary checks (fixed now)
- **Manual review of survivors on executed lines** (all of them, or a seeded random 60 if there are more), single annotator (the author of this plan), with the rubric: **equivalent or unobservable** (the flip cannot change behaviour a caller or test could observe: dead branches, unused values, log text, performance only), **plausible test weakness** (it changes behaviour a reasonable test of that code would assert), **cannot tell**. Labels are written before the join to the full-suite check below is read.
- **Second labeller, disclosed as another model, not as independent verification:** a separate Claude agent given only the diff, the mutated line and its context and the same rubric labels the same survivors without seeing mine; agreement is reported. If agreement is below 70% the plausible-weakness share is reported as **unreliable**.
- **Covered elsewhere (secondary):** for survivors on executed lines of runs whose full project suite runs in 3 minutes or less, the full suite is run once on the mutant; a survivor killed by it is "killed by other tests". Not checked otherwise, and said so.
- **Cost:** wall-clock of the mutation step per run, the number of mutants, and the ratio to the run's single baseline test time.

## 5. Primary outcomes and decision rules (fixed now)
Let R = valid, executed mutants and S = those that survived. Report S/R overall and with a **repository-level cluster bootstrap** (20,000 resamples of repositories, seed fixed; runs of one repository are not independent and several repositories contribute more than one run) and leave-one-repository-out and the share of **all** survivors that are on executed lines (information beyond coverage).
- **Not enough data (Investigate, with what would settle it):** fewer than 100 valid executed mutants, or fewer than 10 runs, or fewer than 8 repositories, contributing any.
- **Proceed** to a pre-registered coverage-only versus coverage-plus-mutation comparison (and consider an opt-in mutation action) if **all hold:** S/R >= 20% with the lower end of the cluster bootstrap interval >= 10%; **at least 50% of the reviewed executed survivors are labelled plausible test weakness** and labeller agreement >= 70%; and the **median mutation-step time per run is at most 10 minutes**.
- **Stop** if S/R < 8%, or fewer than 33% of reviewed executed survivors are plausible test weaknesses, or the median per-run mutation time exceeds 30 minutes.
- **Investigate further** otherwise.
Not claimed whatever the outcome: that mutants represent real agent defects; that mutation score predicts defect detection; anything about other agent families, languages or non-Python code; that surviving means "bad tests" (equivalent mutants, undertested but irrelevant code and tests outside the claimed set all produce survivors).

## 6. Threats stated in advance
Mutants are not real faults and the operator set decides which flips exist; the suite under test is the claimed target tests, not the project's full suite (hence the secondary check); the runs come from one PR-author family (21 of 22 Codex) and small repositories; single human-equivalent annotator plus a model labeller that shares model-family blind spots; live package indexes and today's environment; a run's suite may be too slow for the cap, which biases the sample toward fast suites (reported); the planted-fault study showed that naive flips yield many invalid mutants, hence the tool and the validity filter.

## 7. Deviation log
**Tool-validity step (2026-10-14; before any registered data; its mutant outcomes are discarded).** The smallest rebuildable run (`onyx-dot-app/onyx#3831`, 1 added line) changes a regex string literal, and cosmic-ray enumerates **no mutant** on it, so it cannot exercise the pipeline; the step used the next smallest run with mutable lines (`mfat/sshpilot#331`). What it established, and the rules it adds to section 3 (clarifications written before data collection):
1. **Line restriction works** by deleting the rows of the cosmic-ray session database whose `start_pos_row` is not an added line (`mutation_specs` and `work_items`).
2. **The mutated file is restored after every mutant** (content hash identical before and after).
3. **Sandboxed execution works with the tool**: the test command is the platform-sandbox wrapper plus `env HOME=... TMPDIR=... PYTHONPATH=<repo>/src:<repo>` plus the run's captured interpreter; the command must be written into the TOML config as a **JSON-quoted string** (a Python `repr` produced an invalid TOML string for a command that contains quotes).
4. **A failing baseline silently kills every mutant.** With a malformed command, `cosmic-ray baseline` exited 1 and both mutants were reported KILLED; with the corrected command the baseline passed and both mutants SURVIVED. **New fixed rule: `cosmic-ray baseline` on the exact command must exit 0 before any mutant of that run is counted; otherwise the run is excluded and listed.**
5. **Operator sparsity on agent changes.** Only 2 of the 11 added lines in the validity run had a candidate (the others are imports, calls or strings); across all 18 runs the enumeration gave **287 candidate mutants for 282 added lines** (1.02 per line; per run: 0, 0, 1, 1, 2, 2, 2, 3, 3, 8, 9, 14, 15, 17, 21, 28, 34, 127; **2 runs have none** and one run holds 44% of all candidates, which the cap of 25 per run addresses; counts only: `research/preconditions/mutation_yield_count.py`, no test executed). After the cap the sampling frame is **173 candidate mutants**, of which only those on executed lines are valid executed mutants; with B6's pooled changed-line coverage of about 83% the expected number is roughly 140, so the **>= 100 minimum of section 5 is reachable but not safe**. The thresholds are **unchanged**; if the count falls short the outcome is "not enough data" by the pre-registered rule. A larger population (adding the 37 valid runs of B3-B5 under the same pipeline) is an option for the owner **to decide before any registered mutant is run**; it is not applied.

**Amendment 2 (2026-10-14, owner decision "go with option 2", made after seeing candidate-mutant COUNTS only and no mutant outcome):** the population is enlarged from the 18 rebuildable B6 runs to the 53 rebuildable valid runs of B3-B6 (section 2) because the B6-only frame (173 candidates after the cap; about 140 expected executed) would clear the 100-mutant minimum only barely. Thresholds are unchanged; the cap per run is unchanged; the total wall-clock cap is raised to 8 hours; the bootstrap is by repository and a minimum of 8 contributing repositories is added. Counts: `research/preconditions/mutation_yield_count.py` per stage, data local. Also noted: a bug in the validity-step script applied line numbers from every file's hunks to one file, so its discarded outcomes concerned lines the agent had not changed in that file; the registered harness restricts per file.

**Harness trial (2026-10-14, first registered run `stageb3 mfat/sshpilot#630`):** the coverage export wrote `cov.json` outside the sandbox's writable directories, so every executed-line label came back empty (`coverage_note`). Bug fixed (the file now goes to the scratch directory); that run's output line was **discarded and the run redone**; mutant outcomes were unaffected by the bug (the label is computed separately), and no outcome was used to choose the fix. Any further harness bug will be logged here in the same way.

**Harness bug 2 (2026-10-14, found by reading the exclusions of the first full pass, before any survivor was reviewed or any rate computed):** the coverage step installed `coverage` into the captured environment and uninstalled it afterwards; when the captured environment already contained it (through `pytest-cov`), the uninstall removed the agent's own package and the suite could no longer start, so cosmic-ray's baseline failed for 3 runs (`open-webui-developer-toolkit#174`, `python-statemachine#533`, `cartography#1622`) although the harness's own baseline had passed. Fixed: coverage is installed and removed only if it was absent; those 3 runs are re-run. The other 9 baseline exclusions were diagnosed from the stored output and are genuine environment dependencies, not harness faults: `sqlmesh` x3 (a generated, git-ignored version symbol is missing from a clean rebuild), `localstack` (the project is not importable once its own distribution is dropped from the capture), `instructor` (a test skips without a credential variable), `dspy` (a test starts a local server, which the sandbox forbids), `onefilellm` x3 (the claimed test file contains network integration tests that fail in the network-free sandbox). They stay excluded and are reported as such. Harness diagnostics (`baseline_output`, `MUT_KEEP`, `MUT_ONLY`) were added; they change no outcome.

**Harness bug 3 (2026-10-14, found by the instrumentation check the plan anticipates: 14 mutants were KILLED on lines labelled not executed; first full pass, before any survivor was reviewed):** coverage records a statement by its first line, so a mutant on a continuation line of a multi-line statement, a mutation inside an `except` clause, or one on a default-argument line was mislabelled "not executed", which undercounts R and misplaces survivors. Fix: the mutated line is mapped to its enclosing statement (AST) before the executed/executable lookup; the raw line label is kept alongside; for runs whose executed labels were unavailable the harness now records the coverage run summary and the export error. The whole pass is **re-run** (mutants are sampled with the same seed, so the same mutants; the first pass is kept as `mutation_study_pass1_discarded.jsonl` for comparison, not used). The aggregate outcomes of the first pass had been looked at when this was found; the fix changes labels only, not what is mutated or how it is run.

## 8. Results (2026-10-14; pre-registered rules of sections 4 and 5 applied unchanged; script `analyze_mutation_study.py`, raw data local)
**Flow.** 59 valid runs of B3-B6 considered (B3 11, B4 8, B5 18, B6 22). **Not run:** 7 with no candidate mutant on the added lines; 6 that created files the saved patch lacks; **9 whose sandboxed baseline failed** (genuine environment dependencies, listed in the deviation log: `sqlmesh` x3, `localstack`, `instructor`, `dspy`, `onefilellm` x3). **37 runs ran** (B3 8, B4 5, B5 11, B6 13): 683 candidate mutants enumerated, **421 sampled** (cap 25 per run), outcomes 266 killed, 152 survived, 3 not run, 0 timeouts, 0 incompetent among the sampled. Executed-line labels were unavailable for 3 runs whose captured environment already contained a coverage module (the coverage data file came back empty; 29 mutants): they are **excluded from the join and reported**, not guessed. **389 valid mutants carry labels.** After the statement-mapping fix (harness bug 3) the instrumentation check came out as planned: **0 mutants killed on lines labelled not executed**; for comparison the discarded first pass gave S/R = 26.4% with 14 such mislabelled kills.
**The join.** R (valid and executed) = **348** mutants from **33 runs in 22 repositories**; S (survived) = **103**; **S/R = 29.6%**. Not executed: 41 valid mutants, all 41 survived (coverage already shows these gaps). Of the **144 survivors** with labels, **103 (72%) are on lines the tests executed** (information beyond coverage), 41 (28%) on unexecuted lines. **Repository-level cluster bootstrap** (20,000 resamples of the 22 repositories): S/R **18.7-41.3%** (95%); leave-one-repository-out 27.3-33.9% (lowest without `sshpilot`, which holds 23 of the 103 survivors, highest without `llm-subtrans`). Per stage: B3 34/104, B4 29/64, B5 23/77, B6 17/103 (survivors / executed mutants). By operator family the survivors are mostly constant replacements (40) and comparison flips (27), then `except` clauses (11), arithmetic (8), `and`/`or` swaps (5), negations (5), boolean constants (5).
**Cost.** Mutation-step wall-clock per run: **median 6 s**, maximum 985 s; median 7x one baseline test run; no run hit the 20-minute cap. (Environment builds, not mutants, dominate the total time.)
**Manual review (rubric of section 4; seeded random 60 of the 103 executed survivors, 13 repositories).** Primary annotator: **48 plausible test weakness (80%)**, 5 equivalent or unobservable, 7 cannot tell. Second labeller (a separate Claude agent shown only the packets; **another model, not independent verification**): 52 plausible (87%), 5 equivalent, 3 cannot tell. **Agreement 52/60 = 87%.** **Ordering disclosure:** the second labeller's report reached this session while I was labelling; my labels for packets 1-30 had been fixed before I saw it (30/30 agreement there, 28/30 plausible) and my labels for packets 31-60 were written **after** I had read it, so agreement on 31-60 (22/30) is **not independent**; the plausible share of the independent half is 28/30. The 8 disagreements: five `except ImportError` clauses I labelled cannot-tell because they differ only when an optional dependency is absent (it said plausible), one arithmetic split (`maxsplit` 6 vs 5) I judged plausible and it judged equivalent, one `-1` index I judged plausible (it: cannot tell), one `json.dump(indent=2 -> 1)` I judged equivalent (formatting only; it: plausible). Examples of the labelled equivalents: `args[0]` to `args[-1]` where `len(args) == 1` is already guaranteed. Not done: the secondary "killed by other tests" check against the project's full suite (not run in this pass; it can only lower the plausible-weakness share for survivors the full suite kills).
**Decision under the rules fixed in section 5: PROCEED.** Data sufficiency met (348 valid executed mutants >= 100; 33 runs >= 10; 22 repositories >= 8); S/R = 29.6% >= 20% with the cluster-bootstrap lower bound 18.7% >= 10%; 80% of reviewed survivors plausible (>= 50%) with labeller agreement 87% (>= 70%); median mutation-step time 6 s <= 10 min. "Proceed" means, as pre-registered, a **pre-registered coverage-only versus coverage-plus-mutation comparison** (same changes, a stated cost budget) and consideration of an **opt-in** mutation action: not a claim that mutation testing finds real defects.
**Reading and caveats (not part of the rule).** (1) The survivors are dominated by simple constant and operator flips on default values, boundaries and configuration; "plausible test weakness" there means "a reasonable test could pin this value", which is a weaker kind of gap than a missed logic error, and one fifth of the sampled survivors were equivalent or undecidable. (2) The mutants are not defects, the operator set decides what exists, and the suite under test is the claimed target tests, so a survivor may be killed elsewhere in the project (unchecked). (3) The sample is agent-authored changes from one PR-author family in small repositories, mostly Python packages with simple tests; `sshpilot` contributes a fifth of the survivors. (4) The three-stage population means the captured environments differ in design by stage; the environments were rebuilt by one rule. (5) Review is single-annotator plus a model labeller that shares model-family blind spots. What this adds to the earlier 21-mutant analysis: the survivor rate on executed lines is higher (29.6% against 12.5%) and the result no longer rests on two cases.

## 9. Can real later fixes validate the survivors? Feasibility enumeration (2026-10-15; counts only, nothing joined to mutant outcomes)
Question considered after the PROCEED decision: do lines whose mutants survive get fixed later more often than lines whose mutants are killed? (`research/preconditions/later_fix_count.py`: for each valid run, the merge commit M, the lines the PR added, `git blame --reverse M..tip` for which of them were later changed, and whether the next changing commit has a fix-like subject within a year of M.)
**Result.** Enumerable runs: 30 of 59 (29 skipped because the merge commit could not be identified on the default branch, mostly rebased or re-titled merges). Of **613 added lines**, **137 (22.3%) were changed again later** (any reason), but only **16 lines (2.6%) by fix-like commits within a year**, in **5 runs across 4 of the 21 repositories** (per run: 0 in 25 runs, then 1, 1, 2, 4, 8). Median observable history after the merge: 410 days.
**Decision (written before any join): do not run a predictive-validity test on later fixes.** 16 events in 4 repositories cannot support a confirmatory comparison, and "changed again later" (22%) mostly measures refactoring and feature work, not defects. Adding the 16 fix-changed lines as an anecdotal case study is possible but would be descriptive only. The honest statement is: **the real-world defect value of mutation survivors cannot be proven with the data we have;** what the study shows is that survivors on executed lines are frequent (29.6%) and, in a reviewed sample, mostly describe behaviour a reasonable test could pin. What would prove more: a benchmark of real, reproducible Python bugs with a buggy and a fixed version and the tests that expose them (for example BugsInPy), asking whether mutants on the buggy lines survive the pre-existing tests; the literature on mutants as substitutes for real faults (mostly Java) suggests coupling, which would still need to be re-established for Python agent code. That is a separate, larger study (many projects need old interpreters and dependencies that do not build on a current Python).

**Full-suite check, harness bug 4 (2026-10-15, found by inspecting the baselines before reading any survivor outcome as a result):** the first pass ran pytest without `--continue-on-collection-errors`; in 8 of 20 runs pytest exited with code 2 at baseline after collection errors and ran no tests, so "survived the full suite" there was meaningless (93 of 94 checked survivors had been reported as surviving, 1 killed). Fixed by continuing past collection errors (collection errors count as baseline failures; a mutant is killed only by a failure that the clean baseline does not show) and by reporting runs whose baseline still runs no test (exit code other than 0 or 1) as not checked. The first pass is kept as `mutation_full_suite_pass1_discarded.jsonl`; the whole check is re-run.
