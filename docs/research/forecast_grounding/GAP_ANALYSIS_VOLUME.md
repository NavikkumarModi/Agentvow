# Gap analysis: version control and review for agent-scale VOLUME (2026-10-10)

Framing from the owner: the problem is not that agent PRs are large (ours are small: median 18 lines) but that there are **too many** for a human to review; humans will stay at a high level. Question: can existing systems manage agent-authored change at that volume, or is a new system needed? Source-status: `[read-html]` = fetched page read through a summarising tool, `[snippet]` = search-result summary only, `[abs]` = arXiv abstract page. Nothing here is a novelty claim; it is a first requirements and gap map, not a survey.

## 1. Properties a volume-scale system needs (derived from the challenge, not from any product)
P1 attention allocation: route each change to leave-alone / escalate by risk, not arrival order. P2 independent evidence per change (not the agent's claim), with staleness. P3 human policy at intent level, bounded delegated promotion. P4 grouping of related changes into one decision. P5 plain-language escalation reasons with UNKNOWN visible. P6 attempt provenance and audit. P7 reversibility at change granularity. P8 cross-change interaction (many valid changes, combined behaviour). P9 aggregate view of what the fleet of agents changed. P10 human agency preserved (no silent approval). P11 **replayability**: independent evidence is only possible if the attempt's environment can be re-run.

## 3. What this says
1. **No source found provides evidence-based routing.** Triage exists (2601.00753) but on effort proxies; policy exists (rulesets) but over checks the agent's PR already has; provenance exists (Atomic, GitLab) but attests who made a change, not whether its claim holds. "Route each change by independent evidence of correctness and its unknowns" is a **potential gap requiring further verification**, from a limited search that did not read the products' full documentation.
2. **The binding constraint is P11, not the router.** Our measurements: only 11-19% of real agent PRs reached a usable independent run (a property of reconstructing the environment *after the fact*); agents omit what they take for granted (B2); 48% of honest, evidence-closed patches still had changed lines no test ran. A router over evidence can only leave alone what evidence closes, so today it would escalate most changes. Any new system must therefore capture the executable environment **at attempt time** (a hermetic, re-runnable record) rather than reconstruct it later. None of the systems above was found to record this; they record who/what/why. **Hypothesis, untested:** attempt-time environment capture raises replayability far above 19%.
3. **Is a new platform needed?** The evidence does not show that existing version control must be replaced: Git can remain the store, and the new element would be a layer that (a) records an attempt with its re-runnable environment, (b) attaches independent evidence and unknowns, (c) routes by a human-set policy. Whether that layer is a new platform or an extension of a forge (GitHub, GitLab) or of a VCS (Atomic) is a product-strategy question the data cannot answer; the forges have the distribution and are building adjacent pieces.
4. **What is NOT established:** that humans are in fact overwhelmed at the volumes in question (platform statistics are vendor-reported and not agent-specific); that evidence-based routing reduces human load without more misses (needs a replay study on historical PRs and a human study); that attempt-time capture is practical across languages and services.

## 4. Falsifiable next steps (cheap first)
(a) Using the AIDev data already sampled: estimate the share of agent PRs that a *perfectly replayable* world could close with independent evidence (requires attempt-time capture to emulate: run agents ourselves in a captured environment and measure reachability, compared with 11-19%). (b) Replay 2601.00753's triage on our PR sets to compare effort-based routing with evidence-based routing on recall of real failures. (c) Only then a human attention study.
