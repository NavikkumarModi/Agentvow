# Stage B3 (attempt-time capture vs after-the-fact reconstruction) — pre-registration, 2026-10-10 (written BEFORE any B3 run)

Origin: `GAP_ANALYSIS_VOLUME.md` section 3 hypothesis: a verifier can only close what it can replay; reconstructing the environment after the fact reached 11-19% of real agent PRs; **recording the agent's executable environment at attempt time should raise independent replayability far above that.** B1/B2 cannot test this because their tasks were chosen where reconstruction already worked.

**Question.** On real agent-PR tasks where zero-config reconstruction **failed** (the population B1/B2 excluded), what fraction of runs in which the agent's tests pass in its own environment can be independently reproduced (a) by reconstruction from the repository (the zero-config ladder, as in B1) and (b) from a **capture of the agent's environment** made at attempt time?
**Capture (deliberately simple, stated up front):** the agent's exact `pip freeze` (editable and direct-URL entries dropped, as in B1) plus its Python version and the environment values the session audit finds. It is a weak proxy for a real container snapshot: no system packages, services, generated files or secrets. A positive result is therefore conservative for the capture idea; a negative result does not refute a fuller capture.
**Tasks.** The 199 structural candidates that Stage B0 rejected as "no zero-config environment and no CI recipe" or "no reference environment" (all have target test files at head), seeded random order (seed 2029), at most 2 per repository, up to 24 tasks. Re-posed as in B1 (base commit + the PR's test files, no history, no remote); same agent, S0 sandbox, empty virtualenv, prompt C1P (recipe requested), one run per task. No S1/S2 validity screen: no reference environment is known, so **validity is established from the run itself**: a run counts only if the target tests pass in the agent's environment AND fail on the baseline without the agent's changes (non-triviality, checked in the agent's environment).
**Contexts on the same frozen patch (same scoped target command everywhere):** E_repo (zero-config ladder), E_capture (freeze replay), E_recipe_scoped (the agent's recipe with the scoped test command). Secondary: the agent's own command.
**Primary outcome.** Among valid runs: reproduction rate of E_capture and of E_repo, with Wilson 95% intervals and paired counts. **Pre-registered reading:** capture supports the hypothesis if E_capture >= 70% and exceeds E_repo by >= 30 percentage points; the hypothesis is not supported if E_capture <= E_repo + 10 points; in between, inconclusive. N is small (up to 24 attempted, fewer valid): descriptive only.
**Secondary:** agent success rate on these harder tasks; reasons for capture failures (classified by hand from saved records); recipe results; cost.
**Budget.** Hard cap $15 total, $1.5 per run; stop when the cap or 24 tasks is reached; stop without recording on rate limits.
**Code.** `stageb_run.py` with `CAPTURE=1` (tasks from `stageb3_tasks.jsonl` built by `stageb3_select.py`; output `stageb3_results.jsonl`); instrument = post-fix commit `7d56541` onward. Changes during the run are logged below and affected measures recomputed.
**Known limits stated in advance.** Capture is pip-freeze only; tasks are the population on which reconstruction failed, so they may be harder for the agent too (low agent success reduces N); a run where the agent installs from VCS or local paths has those entries dropped from the capture; one model; one run per task; reconstruction tasks, not natural bug reports; third-party code (snapshots stay local).
