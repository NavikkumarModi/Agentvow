# State of the project (2026-10-28)

Status: a snapshot for the owner. Numbers come from this repository's studies (small, Python-only, mostly one agent family, one annotator). Nothing here claims novelty; where a gap is mentioned it is a "potential gap requiring further verification". Head of `main` at the time of writing: `66e12cc` plus this note.

## 1. What exists
- **Tool.** `agentvow` checks what an agent said against what can be observed. Verdicts come only from deterministic collectors and checkers (CONTRADICTED / SUPPORTED_BY_PRIOR_EVIDENCE / NOT_CONTRADICTED / UNKNOWN); no LLM decides. It informs a person and never approves or merges.
- **Released: 0.4.4** on PyPI (published 2026-10-26; ten releases since 0.1.0 on 2026-10-09), with the GitHub gate workflows defaulting to 0.4.4, the VS Code extension, hooks, receipts and a policy layer (allow / needs_acknowledgement / block).
- **On `main`, not released: 0.4.5.** Statement checkers (files changed or left alone, documentation updated, linter clean), the `description_mismatch` policy key, generic-lint resolution, opt-in environment reconstruction switches. The release is **on hold** by the owner's instruction; nothing is tagged, uploaded or announced. A pilot that runs `pip install agentvow` gets 0.4.4 without these.
- **Control plane service** (OIDC, check runs, acknowledgements) exists and was verified live on GitHub earlier; notification, policy refresh, the fork path and a hosted deployment have never run on GitHub.
- **Quality gates.** 698 Python tests and 32 Node tests; `scripts/validate_all.sh` has been 38/38 at the last full run; CI is green on the last code commit. An adversarial review ran on the statement checkers (8 findings fixed) and on the offline shadow study (findings applied, one reading withdrawn).

## 2. What has been measured, and what it does and does not show
| Question | Result | Reading |
|---|---|---|
| Can the agent's environment be reproduced? (E3, B6) | Captured packages reproduced 16 of 18 replayable runs vs 9 for repository-derived setup; 20 of 22 valid B6 runs (91%) | Reproducibility, pre-registered; small, Python-only, one host |
| Does replay change a decision? (E5, shadow runs 1 and 2) | E5: 1 captured-only flag in 9 faults. Run 2 (controlled, 36 faults): decisions **identical in all 19 faults where both contexts run**; capture differs only where the project-native context cannot run at all | No decision value shown beyond being able to run the tests; 10 faults in 6 runs were "continue" on unseen faults |
| Can statements beyond tests be checked? | Three checkers; precision on ~1,300 real PR descriptions went 56% → 91% over five hand-reviewed rounds; only lint can be CONTRADICTED; files/docs disagreements become attention, not blocks | Useful, conservative; each round found new misreadings; claim coverage rose by about 15 points of 152 labelled statements |
| Can third-party pull requests be reconstructed without the agent's environment? | Four experiments, 27 repository runs (lock files, Python version choice, dependency discovery, CI-derived environment): **0 verdicts gained**, some worse | UNKNOWN is the stable outcome outside plain-pip repositories; stop patching heuristics |
| Detection on real third-party pull requests (v2) | 3 of 83 conclusive | Reachability, not detection, is the gate |

The honest summary: Agentvow has a trustworthy evidence layer and good discipline about uncertainty. It has **not** shown that the layer makes autonomous or semi-autonomous coding measurably safer, nor reduced human review, in a real workflow.

## 3. Prior art and positioning
- Evidence-gated autonomous lifecycles are already described (Proof-or-Stop and similar, only partly read: treat as `[snippet]`). "Evidence controls autonomy" is **not** a novelty claim. The autonomy gate in `docs/research/NOVELTY_BOUNDARY.md` is **not passed**.
- The narrower wedge under test: comparing evidence from the agent's observed context with evidence reconstructed from the project's declared setup, with provenance and uncertainty explicit. Potential gap requiring further verification.
- A supplied capture bundle is unauthenticated: it is checked for binding to the code and replayed, but its origin is not proven.

## 5. The next real test
Offline evidence is exhausted: more injected faults on the same 20 runs will not answer the product question. What is missing is a **shadow-mode run on a plain-pip repository with real agent pull requests and independently labelled defects**, comparing CI-only, project-native and captured-context decisions on autonomous progression, unsafe advancement, false blocks and cost (`SHADOW_STUDY_DESIGN_2026-10-27.md`, step 4). It needs a design partner and a second annotator. Until then the product claim is "an honest independent check that often says UNKNOWN", not "makes autonomy safe".

## 6. Risks
- **Value risk.** CI plus existing gates may already cover what the layer adds; run 2 found no difference where both can run.
- **Reachability risk.** Outside plain-pip repositories the tool mostly returns UNKNOWN.
- **Evidence-quality risk.** One annotator behind every hand-validated number; one agent family; Python only.
- **Trade-off risk.** A context that can run the tests turns honest escalations into "continue" on faults the tests do not see; unsafe advancement against real defects is unmeasured.
- **Process risk.** Several experiments lost time to harness mistakes (own-state classification, stale evidence, a leaking test); each is documented, and the remedy is controls and isolation by default.
- **Deployment risk.** Hosted deployment, notification and fork paths remain unverified on GitHub; the VS Code Marketplace update is unverified.

## 7. Suggested order of work
1. Decide on the 0.4.5 release and on the statement checkers' default (cheap, unblocks pilots).
2. Get one plain-pip repository running the gate in shadow mode (needs a partner).
3. Recruit the second annotator and fix the critical-requirement definitions before looking at outcomes.
4. Only then revisit the autonomy question with real decision data.
