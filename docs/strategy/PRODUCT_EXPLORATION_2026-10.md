# Exploring the proposed direction: what is missing between the tool and the claim (2026-10-20)

Direction under exploration (VISION update, section 8): an independent clean-room replay of an agent's claim from an environment recorded at claim time, with UNKNOWN as a first-class result, never claiming correctness. This note lists what the current tool and evidence do not yet support, ranks the ways to close each gap by evidence value and cost, and pre-registers the first cheap measurement. Status: a plan; one measurement (E1) is started with this note.

## 1. Gaps between the positioning and what exists (checked against the repository)
| gap | today | why it matters |
|---|---|---|
| Strong reconstruction baseline | the zero-config ladder (extras, a fixed requirements list, pytest) is what the tool ships; CI-derived recipes exist only in `research/preconditions/ci_recipe.py` | the paper's headline gap (91% vs 55%) is mostly a weak comparator; the strongest reviewer objection |
| Cross-time | captures pin versions; replay was measured same day only | "reproducible" needs to hold later (yanked or removed wheels) |
| Cross-machine | a Linux sandbox (bubblewrap) exists and CI-tests the tool; B6 replays were all on one macOS host | pinned wheels can differ by platform |
| Replay changes a decision | no run shows a CONTRADICTED caught through capture; `scripts/planted_faults.py` exists from earlier work | without it, the study measures replayability only |
| Second agent | test-time capture verified live on Claude Code only; a Copilot output format exists | one model family everywhere |
| Beyond Python packages | out of scope by design (system packages, services, generated files, secrets) | caps how many claims can be closed; the not-reproduced manifest names what was skipped |
| Real users | pilot kit written; the owner dropped the pilot on 2026-10-21 (see the product plan) | whether people act on UNKNOWN is untested |

## 2. Ranked ways to close them (evidence value against cost; none needs a new agent run unless stated)
1. **E3, strong reconstruction baseline** (highest value). Add CI-config and Dockerfile-derived setup as a further replay context, pre-register, and re-replay the 22 valid B6 runs. Cost: engineering plus replay only. Answers the main objection; the result may shrink the 91-vs-55 gap, and that is a finding either way.
2. **E1, cross-time re-replay** (cheapest; time-dependent so it starts now). Re-replay the 22 valid B6 captures from the saved patches and pip freezes at +8 days now and +30 days later.
3. **E5, a replay that changes a decision.** Inject known faults into the B6 patches (the repository has a planted-fault harness) and test whether capture-based replay turns a false "tests pass" into CONTRADICTED where reconstruction returns UNKNOWN. No agent spend; design must be pre-registered and must not tune faults to the tool.
4. **E2, cross-machine (Linux).** Needs Docker running and an image download (not done; disk is tight, about 6 GB free), 22 replays.
5. **E4, a second agent family.** New agent runs (cost in dollars); only after E3 and E5.
6. **Pilot.** Needs participants the owner recruits.

## 3. Pre-registration of E1 (written before the run)
Population: the 22 valid B6 runs (capture originally passed in 20, inconclusive in 2). Procedure: `research/preconditions/stageb3_recapture.py stageb6 3` (the same fuller capture and 3 GB size limit as the registered B6 replay; runs with untracked files not in the patch are skipped and counted). Outcome: for each of the 20 originally passing captures, whether the replay still passes; for the 2 originally inconclusive ones, whether the result is unchanged. Reading, fixed now: stable if at least 18 of the 20 still pass (90%); any flip is reported with its reason (a missing or yanked package versus a platform or tool change). This is a cross-day check at +8 days (B6 ran on 2026-10-12 and -13), not a cross-month one; the second point at +30 days is added to this note when run. Nothing in E1 is a hypothesis test; it is a stability measurement with one threshold.

## 4. Pre-registration of E3, the strong reconstruction baseline (written before it is run on any B6 task)
**Context E_strong.** Derived deterministically from the repository at the base commit by `research/preconditions/strong_baseline.py` (frozen at the commit that carries this section; later changes would be post-hoc and reported as such): (1) the zero-config ladder's own steps (`pip install .` with the detected test/dev extras, then the existing requirements files from the ladder's fixed list); (2) every `pip install` line in the GitHub Actions workflows (plus tox.ini deps, uv/poetry sync translated to pip, Makefile test targets, literal environment values) through the existing CI extractor; (3) `pip install` lines in Dockerfiles; (4) other requirements files (`requirements*.txt`, `requirements/*.txt`, `*-requirements.txt`, excluding names containing docs, lint, format, typing, mypy, build, release, publish, windows, benchmark); each line validated by the product's recipe validator, at most 12 steps, duplicates removed. The test command is the same scoped target command used in every other context. pytest is supplied if missing, as in every context. Dependency groups are not installable through the recipe vocabulary and are noted. No language model; no outcome of any B6 task was used to design the extractor (it was built from fixtures and from the earlier CI-recipe work), though the author has seen B6 results.
**Population.** The 22 valid B6 runs. Runs whose agent created untracked files that the saved patch lacks (2 of 22 in the E1 re-replay) cannot be rebuilt and are reported as not re-runnable; all comparisons are over the re-runnable runs with each context's original B6 result. Same replay sandbox, 3 GB limit and scoped command as B6; replayed on the same macOS host.
**Outcomes (all reported).** Strong baseline reproduced / re-runnable; paired against capture's B6 result (capture-only, strong-only, both, neither) and against the ladder's B6 result; the gain of the strong baseline over the ladder; the reasons the strong baseline misses.
**Reading, fixed now (mirrors the B6 rule).** Let n be the re-runnable valid runs. *Capture's advantage survives a stronger comparator* if capture reproduces at least 70% and the net paired lead (capture-only minus strong-only) over n is at least 15 points. *Mostly comparator weakness* if the lead is below 10 points or the strong baseline is within 10 points of capture. Otherwise inconclusive. Fewer than 15 re-runnable runs: no reading. This is a descriptive comparison on a feasibility-scale sample, not a hypothesis test, and the result stands whichever way it falls.

## 5. E1 results: cross-day stability of the B6 captures (2026-10-20, 8 days after the original replays; script `stageb3_recapture.py stageb6 3`, output `data/preconditions/stageb6_recapture_2026-10-20.json`)
18 of the 22 valid runs could be rebuilt from the saved patch; 4 could not (the agent created untracked files the patch lacks: open-webui-developer-toolkit#510, AGI-Alpha-Agent#1605, extending-move#16, hlda#39; all four had passed originally). Of the 16 originally passing captures that could be re-replayed, **16 still pass; no flips.** The two originally inconclusive runs: localstack#12976 inconclusive again (missing dependency), instructor#1667 returned no result this time (originally inconclusive, a credential skip).
**Against the pre-registered rule.** The rule was "stable if at least 18 of the 20 originally passing captures still pass". At most 16 of the 20 could be tested, so the rule as written cannot be met; the registration did not anticipate the 4 non-rebuildable runs, and this is stated, not repaired. What is shown: among the captures that could be re-tested, none changed after 8 days. What is not shown: stability over weeks (the +30-day point is still to be run, around 2026-11-12), on another platform, or for the 4 untestable runs.

## 6. E3 results: capture against a strong reconstruction baseline (2026-10-20; frozen extractor at commit `fa7ee6b`; script `b6_strong_baseline.py`; output `data/preconditions/stageb6_strong_2026-10-20.jsonl`)
Re-runnable valid runs n = 18 (the same 4 as in section 5 could not be rebuilt; the registration expected fewer). The pre-registered minimum of 15 is met.
| context (18 re-runnable valid runs) | reproduced |
|---|---|
| zero-config ladder (B6 result) | 10 |
| strong baseline (E3) | 9 |
| capture (B6 result) | 16 |
Paired, capture against the strong baseline: both 9, **capture only 7, strong baseline only 0**, neither 2; net lead 7/18 = **39 points**; capture 16/18 = 89%. The strong baseline gained nothing over the ladder: strong-only 0, ladder-only 1.
**Pre-registered reading: capture's advantage survives a stronger comparator** (capture >= 70% and lead >= 15 points; the lead is also far above the 10-point line for "mostly comparator weakness").
**Why the strong baseline misses (9 of 18).** 6 missing-dependency results (Bindu: uvicorn; hlda#56: numpy; verifiers: datasets; onyx: httpx; things-mcp: things; localstack: localstack), 1 credential skip (instructor, also missed by capture), 1 real test failure (onefilellm, 3 failing tests, also failed under the ladder), and 1 run where the strong baseline did worse than the ladder (cartography#1741: pytest usage error, exit 4, after the added CI steps `pip install -e .`; the ladder passed it). In the missing-dependency cases the files the extractor read (workflows, Dockerfiles, extra requirements files, the ladder's own steps) did not supply the missing packages; I did not check each repository by hand to confirm the packages are undeclared. More steps are not monotonically better: one added step set broke a run the simpler ladder passed.
**Reading with care.** (1) This compares replayability of the agent's own recorded packages against what repository files supply. It does not show capture is a better verifier, only that the gap was not an artefact of a weak ladder. (2) The extractor was frozen before the run and uses only files at the base commit, but the author had seen B6 results, and CI-config, Dockerfile and requirements-file reading is one reasonable strong baseline, not the only one (no README parsing, no dependency-group installs, no interpreter-version selection, no system packages). (3) 18 runs, one model, Python packages, one macOS host. (4) The 4 non-rebuildable runs are excluded from this comparison, not counted as failures; in B6 itself capture passed all four and the ladder passed 2 of them (hlda#39 and AGI-Alpha#1605 did not, from the earlier breakdown).

## 7. Pre-registration of E5, a replay that changes a decision (written before it is run)
**Question.** When the agent's final code has a planted break and the claim stays "All tests pass.", which replay context turns the false claim into something a person sees (CONTRADICTED, or REVIEW REQUIRED), and in which does it stay UNKNOWN or silent? This is the missing "replay changes a decision" evidence. Faults are authored by us, so it measures the pipeline's sensitivity per context, not real-world detection; it says nothing about faults the tests cannot see.
**Population and procedure.** The valid B6 runs whose captured replay passed and that can be rebuilt from the saved patch (at most 16; the others are reported as not re-runnable). For each run, one fault, chosen with a fixed seed (20261022) from a fixed list of operator flips (`==`/`!=`, `<`/`>=`, `>`/`<=`, `return True`/`False`, `and`/`or`, `in`/`not in`) on lines the agent added in non-test source files; a run with no such line is reported as having none. The same faulty working tree is then checked twice with the real tool (`agentvow check --recipe ... --new-test-failures review`, claim "All tests pass.", the same scoped target tests): once with a recipe that installs the captured pip freeze, once with the recipe the product's project-native baseline derives (`agentvow/baseline.py`). `--new-test-failures review` is used because the valid runs' target tests are by construction new or changed and have no baseline; with the default (`unknown`) their failures can only ever be UNKNOWN in every context. Script `research/preconditions/b6_fault_injection.py`.
**Outcome classes per context.** *Flags*: tests_pass verdict CONTRADICTED, or overall status REVIEW REQUIRED. *Silent*: NOT_CONTRADICTED or SUPPORTED. *Unknown*: UNKNOWN without review. A fault is **context-visible** when at least one context flags it; **missed** when no context flags it (these include faults the target tests cannot see and equivalent changes; the oracle is the tests themselves, so nothing here is a miss rate against real defects).
**Reading, fixed now.** Evidence that replay can change a decision: among context-visible faults, captured flags and project-native does not in at least 3 faults, and native flags where captured does not in none (or the exceptions are listed and explained). If captured-only is 1 or 2: weak. Otherwise no evidence. Counts are descriptive on at most 16 faults in at most 16 repositories; one model, one fault per run, macOS only.
**Controls and limits.** The unfaulted state is the E3 comparison already recorded: in E3 the project-native baseline returned a failing result on 2 of 18 clean runs (cartography, onefilellm) where capture passed, so a project-native "flag" can also be the baseline lacking something (a possible false alarm); this is reported next to the fault results, and no fault study can say how often a real user sees such a case.

## 8. E5 results: planted faults under the captured and the project-native context (2026-10-22; script `b6_fault_injection.py`, output `data/preconditions/stageb6_faults_2026-10-22.jsonl`)
**Harness note.** The first pass recorded the wrong field for the reason text (so every UNKNOWN had an empty explanation); it is kept as `stageb6_faults_pass1_no_reason.jsonl` and the study was re-run in full after the fix. **No verdict changed between the two passes.**
**Flow.** 20 valid runs whose captured replay passed: **9 ran** (one fault each); 7 had no plantable line (an operator flip on a line the agent added in a non-test source file); 4 could not be rebuilt from the saved patch (untracked files). One fault per run, seed 20261022.
| outcome (9 faults) | count | runs |
|---|---|---|
| flagged by both contexts (CONTRADICTED, REVIEW REQUIRED) | 2 | korean-romanizer#25, ComfyUI-Lora-Manager#578 |
| flagged by captured only | 1 | verifiers#357 (project-native: missing dependency `datasets`, UNKNOWN) |
| flagged by project-native only | 0 | |
| silent in both (tests did not see the fault) | 1 | jinni#11 (11 passed) |
| silent in captured, UNKNOWN in project-native | 1 | vehicle_speed_estimation#7 (project-native ran 0 tests: 3 skipped) |
| UNKNOWN in both | 4 | hlda#56, llm-subtrans#353, cartography#1741, haliax#184 |
**Why UNKNOWN (from the recorded reason text).** hlda#56: the fault made the suite fail to collect (exit 2, 1 error), so the run is inconclusive. llm-subtrans#353 (34 failed), cartography#1741 (1 failed), haliax#184 (1 failed): the tests that failed also fail without the change, so the tool treats them as environmental ("likely Agentvow's environment") and cannot attribute them to the fault; the valid runs' target tests fail at base by construction, so a fault that breaks one of them leaves no passing baseline to compare with. That is the tool's conservative design working as written, and it is also a real limit: a fault that breaks only tests the change itself added cannot be told from an environmental failure when only the final state is seen.
**Pre-registered reading: weak.** Faults flagged by at least one context: 3. Captured-only: 1 (the rule needed at least 3 for "evidence that replay can change a decision"; 1 or 2 is "weak"), project-native-only: 0. Descriptive, 9 faults in 9 repositories, one fault each, authored by us.
**What can be said.** In the one case where the contexts differ in what a person sees (verifiers#357), the project-native context could not run at all because the dependency was not declared anywhere it read, while the captured environment ran and flagged the fault. In two further cases both contexts flag the fault, so capture added nothing there. In another case the project-native context could not run (0 tests ran, all skipped) while the captured environment ran and stayed silent because the planted fault is not covered by the tests. So the contribution of capture here is mostly "the context could run at all", not "it sees more faults when both can run". Two clean-state project-native failures from E3 (cartography, onefilellm) remain a caveat for any native flag.
**Not shown.** That replay changes decisions on real defects; that results generalise beyond operator flips on added lines; that the UNKNOWNs would resolve with a clean-head baseline (the tool never sees one).

## 9. Pre-registration of E2, the same captures replayed on Linux (written before it is run)
**Question.** Do the B6 captures (the agent's pip freeze) reproduce on another operating system, not only on the macOS host where they were first replayed? Pinned wheels are platform-specific, so this is the cross-machine part of "independent".
**Setup.** A Linux container (Docker Desktop's Linux VM, `linux/aarch64`, Debian, `python:3.13-slim`, the same Python minor version as the macOS replays, so only the operating system and library stack change; plus git and bubblewrap) running the product's own replay (`agentvow check --recipe`, the same scoped target tests, the same fuller capture and 3 GB environment limit, the bubblewrap sandbox). Each task's base commit is cloned afresh and the agent's saved patch applied, exactly as in the macOS re-replays. Script `research/preconditions/b6_linux_replay.py`. The container is throwaway; the user's other Docker images and volumes are not touched.
**Population.** The valid B6 runs whose captured replay passed on macOS and that can be rebuilt from the saved patch (at most 16); the others are listed as not re-runnable.
**Outcome and reading, fixed now.** For each run: pass, or not (with the recorded reason). Stable across operating systems if at least 90% of those runs pass on Linux; every difference is listed with its reason (for example a pinned package with no wheel for this platform, a missing system library, a test that depends on the host). Fewer than 10 re-runnable runs: no reading. Descriptive, one Linux flavour (aarch64 Debian), same day, one model.
**Limits.** The macOS replays used the host's Python 3.13.5; the container has its own Python 3.13.x. The Linux sandbox (bubblewrap inside a privileged container) is not the same isolation as on a developer's Linux machine. This does not test x86-64, other distributions, or the agent's original Python version.

## 10. E2 results: the B6 captures replayed on Linux (2026-10-22; script `research/preconditions/b6_linux_replay.py`; output `data/preconditions/stageb6_linux_2026-10-22.jsonl`)
**Harness history (two discarded passes, kept locally).** Pass 1 compared the claim verdict instead of the test result (a claimed count that differs turns a passing replay into UNKNOWN); pass 2 forgot to copy the PR's target test files into the checkout (the task is "the base commit plus the PR's tests"), so most runs failed with "file or directory not found". Both were harness mistakes, found by reading the reasons, and neither is used. The results below are from the third pass, which ports the study's own `prepare` step and compares the replay's test result.
**Result.** Linux container `python:3.13-slim`, `linux/aarch64`, product replay, bubblewrap sandbox, same fuller capture and 3 GB limit. 20 valid runs had passed on macOS; **16 could be rebuilt from the saved patch** (4 could not: untracked files). **15 of 16 pass on Linux (94%)**; the one that does not is `cartography#1741`: the captured list pins `pymsalruntime==0.20.6`, which has no distribution for this Linux platform, so the install failed and pytest then exited with a usage error (found by running the install by hand: "No matching distribution found for pymsalruntime==0.20.6"). The 4 not re-runnable runs are listed, not counted.
**Pre-registered reading: stable across operating systems** (at least 90% of 16 re-runnable pass: 15/16 = 94%). One flip, and its reason is exactly the cross-platform limit of a pip-freeze capture: a platform-specific pinned package.
**What this adds and does not.** It shows that pinned Python captures made on macOS mostly replay on Linux aarch64 with the same Python minor version. It does not show x86-64, other distributions, other Python versions, or weeks of staleness. The sandbox was bubblewrap inside a privileged container, not a developer's Linux machine.
**A product gap the flip exposes.** When one pinned line cannot be installed, `pip install -r` stops, the environment is missing everything after it (here pytest itself), and the replay reports a confusing pytest usage error instead of the install failure. The recipe path records "setup ... failed" in its notes but the capture replay's result does not carry it. Candidate fix (not built): surface the failed install step and its package in the context's summary and in the next-step advice, and install the remaining lines one by one when `-r` fails.

**Fix built (2026-10-22).** Captured environments now leave out a pinned package pip has no distribution for, install the rest, and report the pin (`recipe.build_env`, `advice.py`, the pack and the finding text); tests in `tests/test_dropped_pins.py`. On the one real case (cartography#1741, `pymsalruntime==0.20.6`) the Linux replay now installs the other pinned packages and the 8 target tests pass; the registered E2 numbers above are unchanged (they were measured before the fix).
