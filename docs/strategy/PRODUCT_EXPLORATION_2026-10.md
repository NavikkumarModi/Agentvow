# Exploring the proposed direction: what is missing between the tool and the claim (2026-10-20)

Direction under exploration (VISION update, section 8): an independent clean-room replay of an agent's claim from an environment recorded at claim time, with UNKNOWN as a first-class result, never claiming correctness. This note lists what the current tool and evidence do not yet support, ranks the ways to close each gap by evidence value and cost, and pre-registers the first cheap measurement. Status: a plan; one measurement (E1) is started with this note.

## 1. Gaps between the positioning and what exists (checked against the repository)
| gap | today | why it matters |
|---|---|---|
| Strong reconstruction baseline | the zero-config ladder (extras, a fixed requirements list, pytest) is what the tool ships; CI-derived recipes exist only in `research/preconditions/ci_recipe.py` | the paper's headline gap (91% vs 55%) is mostly a weak comparator; the strongest reviewer objection |
| Cross-time | captures pin versions; replay was measured same day only | "reproducible" needs to hold later (yanked or removed wheels) |
| Cross-machine | a Linux sandbox (bubblewrap) exists and CI-tests the tool; B6 replays were all on one macOS host | pinned wheels can differ by platform |
| Replay changes a decision | no run shows a CONTRADICTED caught through capture; `scripts/planted_faults.py` exists from earlier work | without it, the study measures replayability only |
| Second agent | test-time capture verified live on Claude Code only; a Copilot output format exists | one model family everywhere |
| Beyond Python packages | out of scope by design (system packages, services, generated files, secrets) | caps how many claims can be closed; the not-reproduced manifest names what was skipped |
| Real users | pilot kit written; no participants | whether people act on UNKNOWN is untested |

## 2. Ranked ways to close them (evidence value against cost; none needs a new agent run unless stated)
1. **E3, strong reconstruction baseline** (highest value). Add CI-config and Dockerfile-derived setup as a further replay context, pre-register, and re-replay the 22 valid B6 runs. Cost: engineering plus replay only. Answers the main objection; the result may shrink the 91-vs-55 gap, and that is a finding either way.
2. **E1, cross-time re-replay** (cheapest; time-dependent so it starts now). Re-replay the 22 valid B6 captures from the saved patches and pip freezes at +8 days now and +30 days later.
3. **E5, a replay that changes a decision.** Inject known faults into the B6 patches (the repository has a planted-fault harness) and test whether capture-based replay turns a false "tests pass" into CONTRADICTED where reconstruction returns UNKNOWN. No agent spend; design must be pre-registered and must not tune faults to the tool.
4. **E2, cross-machine (Linux).** Needs Docker running and an image download (not done; disk is tight, about 6 GB free), 22 replays.
5. **E4, a second agent family.** New agent runs (cost in dollars); only after E3 and E5.
6. **Pilot.** Needs participants the owner recruits.

## 3. Pre-registration of E1 (written before the run)
Population: the 22 valid B6 runs (capture originally passed in 20, inconclusive in 2). Procedure: `research/preconditions/stageb3_recapture.py stageb6 3` (the same fuller capture and 3 GB size limit as the registered B6 replay; runs with untracked files not in the patch are skipped and counted). Outcome: for each of the 20 originally passing captures, whether the replay still passes; for the 2 originally inconclusive ones, whether the result is unchanged. Reading, fixed now: stable if at least 18 of the 20 still pass (90%); any flip is reported with its reason (a missing or yanked package versus a platform or tool change). This is a cross-day check at +8 days (B6 ran on 2026-10-12 and -13), not a cross-month one; the second point at +30 days is added to this note when run. Nothing in E1 is a hypothesis test; it is a stability measurement with one threshold.

## 4. Pre-registration of E3, the strong reconstruction baseline (written before it is run on any B6 task)
**Context E_strong.** Derived deterministically from the repository at the base commit by `research/preconditions/strong_baseline.py` (frozen at the commit that carries this section; later changes would be post-hoc and reported as such): (1) the zero-config ladder's own steps (`pip install .` with the detected test/dev extras, then the existing requirements files from the ladder's fixed list); (2) every `pip install` line in the GitHub Actions workflows (plus tox.ini deps, uv/poetry sync translated to pip, Makefile test targets, literal environment values) through the existing CI extractor; (3) `pip install` lines in Dockerfiles; (4) other requirements files (`requirements*.txt`, `requirements/*.txt`, `*-requirements.txt`, excluding names containing docs, lint, format, typing, mypy, build, release, publish, windows, benchmark); each line validated by the product's recipe validator, at most 12 steps, duplicates removed. The test command is the same scoped target command used in every other context. pytest is supplied if missing, as in every context. Dependency groups are not installable through the recipe vocabulary and are noted. No language model; no outcome of any B6 task was used to design the extractor (it was built from fixtures and from the earlier CI-recipe work), though the author has seen B6 results.
**Population.** The 22 valid B6 runs. Runs whose agent created untracked files that the saved patch lacks (2 of 22 in the E1 re-replay) cannot be rebuilt and are reported as not re-runnable; all comparisons are over the re-runnable runs with each context's original B6 result. Same replay sandbox, 3 GB limit and scoped command as B6; replayed on the same macOS host.
**Outcomes (all reported).** Strong baseline reproduced / re-runnable; paired against capture's B6 result (capture-only, strong-only, both, neither) and against the ladder's B6 result; the gain of the strong baseline over the ladder; the reasons the strong baseline misses.
**Reading, fixed now (mirrors the B6 rule).** Let n be the re-runnable valid runs. *Capture's advantage survives a stronger comparator* if capture reproduces at least 70% and the net paired lead (capture-only minus strong-only) over n is at least 15 points. *Mostly comparator weakness* if the lead is below 10 points or the strong baseline is within 10 points of capture. Otherwise inconclusive. Fewer than 15 re-runnable runs: no reading. This is a descriptive comparison on a feasibility-scale sample, not a hypothesis test, and the result stands whichever way it falls.

## 5. E1 results: cross-day stability of the B6 captures (2026-10-20, 8 days after the original replays; script `stageb3_recapture.py stageb6 3`, output `data/preconditions/stageb6_recapture_2026-10-20.json`)
18 of the 22 valid runs could be rebuilt from the saved patch; 4 could not (the agent created untracked files the patch lacks: open-webui-developer-toolkit#510, AGI-Alpha-Agent#1605, extending-move#16, hlda#39; all four had passed originally). Of the 16 originally passing captures that could be re-replayed, **16 still pass; no flips.** The two originally inconclusive runs: localstack#12976 inconclusive again (missing dependency), instructor#1667 returned no result this time (originally inconclusive, a credential skip).
**Against the pre-registered rule.** The rule was "stable if at least 18 of the 20 originally passing captures still pass". At most 16 of the 20 could be tested, so the rule as written cannot be met; the registration did not anticipate the 4 non-rebuildable runs, and this is stated, not repaired. What is shown: among the captures that could be re-tested, none changed after 8 days. What is not shown: stability over weeks (the +30-day point is still to be run, around 2026-11-12), on another platform, or for the 4 untestable runs.

## 6. E3 results: capture against a strong reconstruction baseline (2026-10-20; frozen extractor at commit `fa7ee6b`; script `b6_strong_baseline.py`; output `data/preconditions/stageb6_strong_2026-10-20.jsonl`)
Re-runnable valid runs n = 18 (the same 4 as in section 5 could not be rebuilt; the registration expected fewer). The pre-registered minimum of 15 is met.
| context (18 re-runnable valid runs) | reproduced |
|---|---|
| zero-config ladder (B6 result) | 10 |
| strong baseline (E3) | 9 |
| capture (B6 result) | 16 |
Paired, capture against the strong baseline: both 9, **capture only 7, strong baseline only 0**, neither 2; net lead 7/18 = **39 points**; capture 16/18 = 89%. The strong baseline gained nothing over the ladder: strong-only 0, ladder-only 1.
**Pre-registered reading: capture's advantage survives a stronger comparator** (capture >= 70% and lead >= 15 points; the lead is also far above the 10-point line for "mostly comparator weakness").
**Why the strong baseline misses (9 of 18).** 6 missing-dependency results (Bindu: uvicorn; hlda#56: numpy; verifiers: datasets; onyx: httpx; things-mcp: things; localstack: localstack), 1 credential skip (instructor, also missed by capture), 1 real test failure (onefilellm, 3 failing tests, also failed under the ladder), and 1 run where the strong baseline did worse than the ladder (cartography#1741: pytest usage error, exit 4, after the added CI steps `pip install -e .`; the ladder passed it). In the missing-dependency cases the files the extractor read (workflows, Dockerfiles, extra requirements files, the ladder's own steps) did not supply the missing packages; I did not check each repository by hand to confirm the packages are undeclared. More steps are not monotonically better: one added step set broke a run the simpler ladder passed.
**Reading with care.** (1) This compares replayability of the agent's own recorded packages against what repository files supply. It does not show capture is a better verifier, only that the gap was not an artefact of a weak ladder. (2) The extractor was frozen before the run and uses only files at the base commit, but the author had seen B6 results, and CI-config, Dockerfile and requirements-file reading is one reasonable strong baseline, not the only one (no README parsing, no dependency-group installs, no interpreter-version selection, no system packages). (3) 18 runs, one model, Python packages, one macOS host. (4) The 4 non-rebuildable runs are excluded from this comparison, not counted as failures; in B6 itself capture passed all four and the ladder passed 2 of them (hlda#39 and AGI-Alpha#1605 did not, from the earlier breakdown).
