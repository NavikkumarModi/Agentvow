# Agentvow 0.4.5

Agentvow checks what a coding agent says it did against what it can independently observe. It informs you; it never approves, rejects or merges, and no language model decides a verdict. Still a prototype, not a safety verdict.

## Changed: the default policy asks a person in two more situations
1. **A change that could have shaped its own test output** (`harness_warning`). A passing result is no longer simply allowed when the change **modified an existing test file, added or edited a file that runs when tests start** (`conftest.py`, `sitecustomize.py`, `usercustomize.py`, a `.pth` file, a test package's `__init__.py`) **or changed the test runner's configuration** (`pytest.ini`, `.coveragerc`, or pytest and coverage settings in `pyproject.toml`, `setup.cfg`, `tox.ini`). A named person acknowledges such a result; set the rule to `allow` in your policy file to keep the old behaviour, or `block`. The receipt records the reason per claim (`modified_test_file`, `autorun_file`, `test_config`).
2. **A description that disagrees with the change** (`description_mismatch`, new). If the agent's message or the pull request description says it changed, added, removed or left alone a file, or updated the documentation, and git's list of changed files says otherwise, the result is shown to a person. It is not a block: see "How reliable" below.

**What this means in practice:** a pull request that edits an existing test file, or whose description names a file it does not touch, now needs an acknowledgement under the default policy. Ordinary changes are unaffected. **A policy file that uses either new key is rejected by Agentvow 0.4.4 and earlier** (an unknown key blocks): pin the gate's `agentvow-version` to 0.4.5 or later, and, if you run the control plane service, raise `AGENTVOW_CP_MIN_TOOL_VERSION` to 0.4.5 so a caller cannot choose an older version to avoid the rules.

## New: three more kinds of statement are checked
- **Files changed or left alone** ("added `x.py`", "I did not touch `y.py`"), from git's own change list.
- **Documentation updated** ("updated the README"): a documentation file is among the changed files; "documentation" with only Python files changed is UNKNOWN because the agent may mean docstrings.
- **A linter is clean** ("`ruff check` passes", also `ruff format`, `black`, `flake8`; "lint passes" with no tool named is resolved from the repository's own `ruff` / `black` / `flake8` / `pre-commit` configuration): the linter is run in the test sandbox, the repository read-only, on the changed Python files; the tool must already be installed and its version is reported; any other tool is UNKNOWN.

Statements of these three kinds never amount to support on their own: a message that only makes them adds an UNKNOWN "no claim about tests or impact" finding.

## How reliable
- **Mismatches** were real in 60% to 91% of cases over five rounds on about 1,300 real agent pull-request descriptions, with every flagged case read by hand, and each round still found a new kind of misreading (that is why a mismatch asks a person and does not block). The real ones are mostly a description naming a file the change does not touch, or a file it says it created that is absent.
- **Extraction is conservative and misses most phrasings** (recall about 36% on a hand-labelled set): only an explicit verb next to a backticked path counts.
- **The linter check covers Python tools only.** On 371 real lint statements the runnable share is 24%; the rest are mostly TypeScript, JavaScript and Go changes, which are UNKNOWN. A clean result is UNKNOWN with attention when the change edits lint configuration or adds a file-level suppression. flake8 is refused when the repository configures local plugins.
- An adversarial review of these checkers found eight issues (flake8 plugins, linter output reaching the report, a lone file statement counting as an allow, path tricks, a timeout leaving processes, and more); all are fixed and tested. The Linux sandbox path of the linter runs in CI (green on ubuntu and macos).

## Not changed, measured: rebuilding a third-party environment
Three opt-in options exist and are **off by default**: `AGENTVOW_LOCK=1` (install from the repository's lock file), `AGENTVOW_PYVERSION=1` (build with the Python version the repository supports), `AGENTVOW_DISCOVER=1` (install sub-projects and requirements files beyond the root). On the repositories whose replay was inconclusive they gained no verdict (27 repository runs; one repository got worse), and the gate's CI-derived environment gave the same outcomes as the zero-config ladder. **For a third-party pull request in a repository whose environment is not plain pip, UNKNOWN remains the stable outcome**; where verdicts come from is an agent's captured environment (91% of valid runs reproduced in the registered test) and plain-pip repositories. Details: `docs/research/` (`LOCK_FILE_EXPERIMENT.md`, `PYVERSION_EXPERIMENT.md`, `DISCOVER_EXPERIMENT.md`, `PACK_EXPERIMENT.md`, `INCONCLUSIVE_CLASSIFICATION.md`).

## Known limits
As before: Python repositories only; capture covers Python packages, not system packages, services, generated files or secrets; running tests needs macOS or Linux; a pass is evidence to weigh, not verification. The same code hidden in ordinary source or in an extra test file is still believed without a question (a pinned, documented limit of replaying a repository's own test code). The notification, the policy refresh and the fork path of the control plane have not run on GitHub. The statement checkers were evaluated on descriptions, not on a deployed gate.
