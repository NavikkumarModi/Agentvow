# Can Coding-Agent Passing Test Results Be Independently Reproduced? A Feasibility Study of Attempt-Time Dependency-State Capture

*Working draft v2, revised 2026-10-15 after an adversarial review (a feasibility / negative-results framing; the review's edits are applied and its counts added)  — first written 2026-10-12 (one paper; the capture study B6 is the primary result, earlier studies are separately labelled stages). The v1 draft, framed around agent-declared recipes, is kept as `DRAFT_v1_recipe_framing.md`. Every number is from this repository's studies; registered and post-hoc analyses are labelled separately. Novelty is stated only as a potential gap requiring further verification (`docs/research/forecast_grounding/PRIOR_ART_2026-10-10.md`).*

## Abstract
A coding agent's "the tests pass" is true in the agent's own environment; whether anyone else can reproduce it is a separate question. We freeze the patch of a real agent-authored pull-request task and ask whether the passing target tests can be independently reproduced in a clean sandbox, under three contexts: reconstruction of the environment from the repository (a zero-config heuristic), a recipe the agent itself declares, and a **capture of the agent's Python dependency state taken at the moment it ran its tests**. No language model is in any verdict; "unknown" is a first-class outcome. In the primary, pre-registered study (B6), 40 tasks were drawn at random without reference to any earlier reconstruction result and a Claude Code agent worked each in an empty environment; of 22 valid runs (agent's tests pass; they fail without its changes), **attempt-time capture independently reproduced 20 (91%, 95% CI 72-97) against 12 (55%, 35-73) for repository reconstruction; capture alone reproduced 8, reconstruction alone 0** (exact paired test p = 0.008; the paired difference is 36 points, Newcombe 95% interval 15-55, whose lower bound sits at the 15-point threshold; post-hoc checks, reported in section 5.3, point the same way), against a rule fixed before the run (capture >= 70% and a >= 15-point paired lead; the 15-point lead was chosen after B1-B5, before any B6 data; 22 valid runs against a registered floor of 20). The comparator is a weak zero-config heuristic (of its 10 misses, 7 are UNKNOWN because it found no dependencies to install, 1 produced no result, 1 is a credential skip that capture also missed, and 1 is a real test failure), and capture replays the environment in which the tests already passed, so capture is best read as an upper-bound control for whether the agent's environment is replayable, not as a competing reconstruction method. The study measures replayability only: no run shows capture changing a verdict or catching a false claim, the replay ran on the same macOS host on the same day, and the capture comes from the claimant's own environment, so "independent" means independent of the sandbox, not of the claimant. The result is feasibility-scale: one model, 22 valid runs, Python packages only (the two misses were a package-layout limit and a credential), and reproduction is not correctness. Earlier stages are reported as development and exploration: agent-declared recipes did not improve on repository replay in two selected cohorts, and the capture design changed after the first three capture studies (inconclusive or underpowered), which is why B6 was fixed and run on fresh tasks. We also report the instrument defects that only real repositories exposed, and release the tool.

## 1. Introduction
An agent's "tests pass" is true under conditions the reader cannot see: installed packages, environment variables, generated files, an interpreter. Prior work measures whether agents can build environments (SetupBench), whether declared dependencies match what executes (Vangala & Malik, 2610.00425), and whether an agent's self-reported capabilities survive hidden probes (ResearchEnvBench); these statements were checked against the PDFs (section 7). None of them, as far as that reading shows, takes a *specific completion claim on a real merged agent pull request*, freezes the patch, and compares independent replay contexts, including a capture made when the claim was produced. One possible gap, not verified against all prior work (two tools could not be resolved and our searches may have missed work), is that unit of analysis; it is a **potential gap requiring further verification**, not an established novelty.
**Research question.** Does capturing the Python dependency state at the time a coding agent runs its tests make its passing claims more independently reproducible than reconstructing the environment from repository declarations?
**Contributions (bounded).** (1) A claim-level, multi-context replay protocol with explicit support basis and verdict classes. (2) A pre-registered feasibility result for attempt-time capture on a random task sample (B6). (3) The record of how the capture design was developed, including inconclusive and underpowered stages and a size-guard defect that masqueraded as missing dependencies. (4) Bounded negative results for agent-declared recipes. (5) Real-repository instrument failure modes. (6) An open-source, fail-closed, deterministic replay tool.

## 2. Instrument and evidence model
**Claims and verdicts.** Claims are extracted from the agent's final message by deterministic pattern rules (when none is found, a fixed sentence is substituted: 8/32 runs in B1 and 13/32 in B2; the replayed object is the agent's target tests, not its wording). Verdict classes: CONTRADICTED / SUPPORTED_BY_PRIOR_EVIDENCE / NOT_CONTRADICTED / UNKNOWN; `REVIEW REQUIRED` is a status and staleness a freshness property; UNKNOWN is never converted into confidence. No language model decides a verdict; an agent's recipe is an untrusted proposal.
**Sandboxed replay.** Tests run in a platform sandbox (macOS `sandbox-exec`, Linux bubblewrap) with no credentials; environment setup uses the network with unpinned names (so replay depends on live package-index state; determinism was measured same-day only). Guards found by adversarial review and real runs: fail closed when no environment can be built; refuse setup that installs the project's own name; refuse symlinked or file-modifying `prepare`; require the command to execute the changed tests; downgrade CONTRADICTED to UNKNOWN when the change edits dependency manifests (post-hoc, in-sample); resource guards (size, disk, timeout) stop an install and the result states that the environment could not be built (before this was fixed, a size-guard stop produced a misleading "missing dependency", see section 5.2).
**Contexts on one frozen patch.** *E_repo*: the zero-config ladder, a heuristic (`pip install .[test|tests|testing|dev|develop]`, a fixed list of requirements files, dependency groups, plus pytest), not a statement of what the repository declares. *E_recipe*: a recipe `agentvow-recipe/1` the agent writes (pip installs, an optional repository script that may only create files, a pytest/unittest command, plain environment values), validated against a closed vocabulary; the scoped variant replaces the agent's test command by the claimed target tests. *E_capture*: the agent's `pip freeze` taken after its run, with `pip` dropped, `setuptools` and `wheel` kept, editable and direct-URL entries dropped and the project's own distribution removed, replayed in a clean environment; it is a Python-package capture only (no system packages, services, generated files or secrets).

## 3. Instrument development (not evidence about agents)
**Reachability funnel (detection study, 140 real agent PRs, registered).** With the registered zero-config ladder, 15/140 (11%) reached a usable run (the base suite has a passing test); a sensitivity arm that installs named missing modules (added after 13 rows had been seen) brought it to 27/140 (19%, 95% CI 14-27). Among 7 usable CI-failed PRs in the registered arm, 1 was CONTRADICTED; among 13 in the combined set, 2 (real regressions, hand-checked). One false alert on a control (foamlib#453) came from a dependency-version mismatch and led to a post-hoc, in-sample guard. These are properties of the tool and its criterion, not claim-level prevalence.
**Designed pilot (12 tasks, 36 runs, one model, registered).** Traps with environment state hidden from the repository: zero-config replay reproduced 42-50% of correct runs, the agent's recipe 75-83%, with 19/20 expressible recipes sufficient. The traps were designed around hidden state; this is an instrument test, not a rate. Stage A (24 runs) showed twice-identical replay in 24/24; the validator rejected none of the 24 recipes, so its safety rests on unit and red-team tests.

## 4. Exploratory studies of agent-declared recipes (B1, B2): bounded negative results
**B1 (feasibility, 32 real PRs from 22 repositories, empty environment, $13.30).** The target tests passed in the agent's environment in 32/32. Repository reconstruction reproduced 31/32 (97%); the agent's recipe 24/30 as registered (24/32 counting two rejected recipes as failures; 26/30 after instrument fixes, post-hoc); the agent's exact `pip freeze` 31/32. The registered hypothesis H1 (recipe reproduces more than repository replay) was not supported (recipe-only 0 runs, repository-only 7). Tasks were selected because zero-config replay already reproduced the PR's own head tests, so H1 was not testable and its non-support reflects that ceiling.
**B2 (same 32 tasks with 17 common packages preinstalled in the agent's environment, one scoped command everywhere, registered falsification rule, $14.90).** Repository reconstruction 31/32 (97%), recipe (scoped) 15/32 (47%), own command 12/32 (38%), freeze 28/32 (88%). 11 of the 17 recipe failures were an omitted `pytest`; a post-hoc runner-supplied change recovered 5 of 10 reconstructable re-replays (about 20/32, 63%), the rest exposing further undeclared packages. The pre-registered reading (repository reconstruction >= 90% means the small-gap reading survives) held. The ladder installs pytest itself, an asymmetry favouring it.
*Reading of section 4.* On real repositories filtered to be reconstructable, reconstruction reproduced nearly everything even with a loaded agent environment, and agent-declared recipes were the fragile context (omitted runners and packages, vocabulary rejections: 6 of 63 recipes written, with two haliax tasks counted in both studies). Neither cohort could show that recipes help or do not help where hidden state matters. The S2 screening (CI parsing for tasks needing outside setup knowledge) yielded 2 of 302 attempts: this characterises that route only.

## 5. Attempt-time capture
### 5.1 Development stages (B3-B5): disclosed because the design changed
The capture was developed in four registered or post-hoc steps on tasks drawn from candidates on which reconstruction had already failed (so reconstruction was low by construction):
| stage | design | result |
|---|---|---|
| B3 (registered) | simple pip-freeze capture; 19 attempted; 11 valid | capture 5/11 vs reconstruction 0/11: inconclusive against the registered bar (70%) |
| B3 repaired (post-hoc, not registered) | keep setuptools/wheel, drop the project's own distribution, fix an isolation false positive | 8/11 |
| B4 (registered, fresh tasks) | repaired capture; 22 attempted; 8 valid | below the registered minimum of 10: no reading; descriptively 5/8 vs 2/8 |
| B5 (registered, fresh tasks) | repaired capture; 38 attempted; 18 valid | 9/18 (50%) vs 3/18 (17%): inconclusive; post-hoc finding below |
### 5.2 A measurement defect that looked like missing dependencies (B5)
Five B5 capture failures reported a "missing dependency" although the package was pinned in the captured list. The cause (verified on one run) was Agentvow's own 700 MB environment-size guard killing the install, after which tests ran in a partial environment. With the limit raised to 3 GB (a documented setting, `AGENTVOW_MAX_ENV_MB`), 4 of the 5 passed (post-hoc: capture 13/18, 72%). The result text for a guard stop now says the environment could not be built. We report this because a fixed resource limit silently converting build failures into dependency verdicts is a general risk for replay-based verification.
### 5.3 Primary study B6 (pre-registered; capture, replay and thresholds fixed before any run)
**Design.** 40 tasks drawn at random from 747 structural candidates (agent-authored PRs with Python tests) not used in B1-B5, without reading any earlier screening or reconstruction result, at most two per repository (31 repositories); the selection script is `research/preconditions/stageb6_select.py` (seed 2032, commit `78f59d6`, the same commit as the pre-registration `STAGE_B6_PREREG.md`). Claude Code (installed default, S0 sandbox), empty environment, one run per task, replay size limit 3 GB, the same scoped target command in every context. A run is *valid* if the agent's target tests pass in its own environment and fail on the baseline without its changes. **Rule (fixed in advance):** supported if capture >= 70% and the net paired lead over repository reconstruction (capture-only minus repository-only, over valid runs) >= 15 points; no incremental value if capture <= repository + 10 points or lead < 10 points; underpowered if fewer than 20 valid runs. The lead threshold is below the 30 points used for B5 because B5's cohort had been selected on reconstruction failure; this was decided before B6 data. The run stopped once at 21 tasks when the disk filled; the stop was disk-driven, not data-driven, but the 21-task numbers were seen (logged) before the registered plan resumed.
**Funnel.** 40 attempted; 1 setup failure; 39 ran; 30 with the agent's tests passing (one of them with an agent error), 9 without (four with an agent error; 5 agent errors in all); of the 30, 8 trivial (the tests also pass without the changes); **22 valid** (19 repositories; 21 from PRs authored by one agent family, although every run used Claude Code).
**Result (on the 22 valid runs).**
| outcome | count |
|---|---|
| both reconstruction and capture reproduced | 12 |
| capture only | 8 |
| reconstruction only | 0 |
| neither | 2 |
| context | reproduced / valid | 95% CI | / agent-passing (30) | / attempted (40) |
|---|---|---|---|---|
| reconstruction (zero-config) | 12/22 = 55% | 35-73 | 16 | 17 |
| **capture** | **20/22 = 91%** | 72-97 | 25 | 26 |
| recipe, scoped | 17/22 = 77% | 57-90 | 21 | 23 |
Exact paired sign test (8 vs 0): two-sided p = 0.008 (descriptive; runs cluster by repository). **Pre-registered reading: supported at the minimum power boundary** (22 valid runs against a floor of 20; the fourth capture study; the lead threshold was set after B1-B5). Consistency: at the interim look (21 attempts) capture was 11/13 and reconstruction 6/13; the 19 later tasks added 9 valid runs (capture 9, reconstruction 6).
**The two capture misses.** localstack#12976: the capture removed the project's own distribution and the repository's importable package is not at the repository root, so the project was not importable (a capture-design limit). instructor#1667: the tests skip without a `GOOGLE_API_KEY` (a credential outside the captured packages; capture should not carry secrets). Five of the 22 valid runs had a recipe rejected before replay (vocabulary friction as before).
**Robustness (post-hoc, `analyze_stageb6_robustness.py`; not part of the registered rule).** (a) Requiring at least one *executed passing test* for a reproduction changes one run: a repository "pass" in `vehicle_speed_estimation#7` had 3 tests skipped and none passed, so reconstruction falls to 11/22 (50%, CI 31-69) and the capture-only count rises to 9 (net lead 41 points); capture stays 20/22. (b) The 8 capture-only runs are spread over 8 different repositories (none has more than 2 valid runs), 8 of 19 repositories show a net capture advantage and none a net reconstruction advantage; a repository-level cluster bootstrap (20,000 resamples of the 19 repositories, fixed seed) gives a capture-rate interval of 76-100%, a reconstruction interval of 26-73% and a net lead of 18-65 points, with no resample at or below zero; leaving out any one repository leaves capture at 90-95% and the net lead at 35-45 points. These bound the clustering concern for this sample; they do not remove the single-model and single-PR-author-family limits.
**Counts added after the adversarial review (post-hoc, from the raw B6 records).** *Reconstruction misses, exact breakdown (10 of 22):* 7 UNKNOWN because the ladder found no dependencies to install (Bindu, hlda twice, localstack, verifiers, onyx, things-mcp), 1 with no ladder result at all (AGI-Alpha-Agent 1605), 1 credential skip (instructor 1667; capture also missed it), 1 real test failure (onefilellm 71; 3 failed tests). Capture passed all of the 7 and the 1 with no result except localstack, and passed the real-failure run, i.e. in that run reconstruction ran the tests and they failed. *Skipped or zero-pass "passes":* among passing results, reconstruction 1 of 12 had zero passed tests (the vehicle_speed_estimation case above), capture 1 of 20 had some skipped tests with others passing, none with zero passed; the recipe arm 1 of 17 had some skipped. *Import-path leniency:* the replay puts the repository root and `src` on the import path in every arm; its effect was **not measured** (it would need a second replay on a clean checkout without those entries). As a proxy only, 2 of the 20 capture passes touch files under `src/`. *Paired difference:* 36 points, Newcombe 95% interval 15-55 (the registered threshold was 15). *Hypothesis count:* capture was tested in four successive studies (B3-B6) with changed designs between them; B6 is the confirmatory one, but readers should weigh it as the fourth.
**What it shows and does not show.** For a random sample of real agent-PR tasks, recording the agent's installed Python packages and replaying them in a clean sandbox independently reproduced 91% of valid passing results, against 55% for reconstructing from the repository, and no result was reproduced by reconstruction that capture missed. It does not show that the reproduced results are correct (the replay reproduces the agent's own run with its own pins); it says nothing about system packages, services, generated files or secrets; and capture replays the agent's environment, so it does not show the repository is self-sufficient.

## 6. Threats to validity
Selection: B1/B2 are conditioned on reconstruction success and B3-B5 on its failure; only B6 is unconditioned (and its candidate pool is the AIDev structural filter, dominated by a few agents and repositories). Garden of forking paths: the capture design was changed after B3 and B5 results; B6 is the confirmatory test and used fresh tasks with a frozen protocol, but the thresholds' lead component was set after seeing earlier stages. Interim look in B6 (disclosed). One model family and one run per task; 22 valid runs from 40 attempts (agent errors, unsolved and trivial tasks lose more than half); reconstruction tasks (PR tests applied to the base commit), not natural bug reports; small changes (median about 18 lines); public repositories the model may have seen. The comparator E_repo is a heuristic ladder, not every possible reconstruction, and installs pytest itself, while the capture side includes `pytest` only because it was in the agent's own freeze. The 3 GB size limit and the rest of the capture design were fixed after B3-B5 results (a forking path, now frozen for B6, which is why B6 uses fresh tasks). Setup uses live package indexes (same-day determinism only). The replay places `src` and the repository root on the import path, which can make imports succeed that a clean checkout would not resolve. Independence: the agent authors the recipe that is replayed, and the capture is taken from an environment the agent controls; neither is a defence against a deceptive agent, and no deceptive agent was studied. Post-hoc analyses are labelled and never replace registered results. Further threats: the manifest-edit downgrade of CONTRADICTED to UNKNOWN in section 2 was added post hoc and was evaluated in-sample; every replay ran on one macOS host with a sandbox, so this is not cross-machine reproduction, and with pinned transitive packages it was not tested after the same day (yanked or platform-specific wheels could break it later); the valid set is conditioned on the agent's success, so it describes tasks the agent can solve non-trivially, 21 of 22 from one PR-author family and many small repositories (the two capture misses are the two with real infrastructure); one run per task gives no estimate of agent variance; and the fixed claim sentence substitutes for the agent's own claim in some earlier-stage runs, so the verified object is the target tests, not the claim.

## 7. Related work
*Source status: the arXiv items below were read in full from the PDFs on 2026-10-15 (`[read-pdf]`); the tool repositories were read from their GitHub READMEs on the same day (`[read-readme]`, the README is the author's description, not an independent evaluation). Tycho and x-harness could not be resolved to a unique repository and are not characterised. Details in `PRIOR_ART_2026-10-10.md`, update 4.*
**Environment synthesis benchmarks.** SetupBench `[read-pdf]` (arXiv:2507.09063; 93 curated tasks; success is a deterministic one-line validation command run in a fresh subprocess after the agent's last action; omitted test tooling such as `tox` is a documented failure, in the coveragepy instance the agent ignored `tox.ini`; no check of the agent's own completion claim) and ResearchEnvBench `[read-pdf]` (arXiv:2603.06739; 44 research repositories created after 2024-01-01; a "capability hallucination" metric C5 compares the agent's self-reported success with hidden probes; no merged PRs). Our "omitted `pytest`" finding resembles SetupBench's, and auditing a self-report against an independent probe is established by ResearchEnvBench; what differs is the claim (a test result on a frozen merged-PR patch) and the comparison of replay contexts including attempt-time capture.
**Dependency reproducibility of generated software.** Vangala & Malik arXiv:2610.00425 `[read-pdf]` (an AI Magazine article, v1 dated 30 September 2026; three agents, four languages, fifty tasks; its text reports 1,000 curated project instances while its figures count 600 first-attempt instances, which we do not reconcile; three dependency layers, declared, installed and runtime-traced; it explicitly labels declared-but-never-loaded packages "overclaimed"). This is an audit of an agent's *dependency claims* against an observed runtime trace, so claim-versus-observation checking of environment statements is not new; it does not check a claim that tests pass. Its predecessor arXiv:2512.22387 `[read-pdf]` (300 generated projects, three agents; 205 of 300 (68.3%) ran out of the box with declared dependencies, Python 89.2%, JavaScript 61.9%, Java 44.0%; the paper's own runtime-expansion statements are internally inconsistent, 13.5x average in the abstract against a 17x figure in the text with JavaScript showing almost none, so we cite no expansion figure). Their object is a newly generated project and its manifest.
**Receipts for agent claims.** `truth` `[read-readme]` (a Rust CLI and MCP server; a language model only parses the claim and a fixed-rule engine decides; a "tests pass" claim is supported only by a recorded run made through `truth run` or a hook after the last edit; it never runs the command itself; its author reports that 30% of failed SWE-agent attempts still claimed success, an unverified figure we do not rely on); Trial `[read-readme]` (a rules-file convention asking an agent to attach a receipt to each claim; the author benchmark is six runs per arm on one fixture); ProofRun, yebiguo/ProofRun `[read-readme]` (a Go tool: it runs the check itself in the agent's environment, binds the result to the git commit plus a hash of uncommitted changes, reports PASS/FAIL/STALE/NOT RUN, no LLM, states that a receipt from an earlier real run is not defended against rollback); Proofrail `[read-readme]` (a public-alpha Python tool that compares an agent's claims with a commit range and submitted evidence and reports verified, contradicted, unsupported or human-review). This mechanism space is occupied, and we claim no new verification mechanism. None of the four, as described in their READMEs, re-executes the result in a separate clean environment and compares execution contexts; ProofRun and truth record or demand a run in the agent's own environment. Our attempt-time capture records state at claim time but is used differently: for an independent re-execution whose result is compared with reconstruction from the repository, on a pre-registered sample.
**Triage and review of agent PRs** `[read-pdf]`. arXiv:2601.00753 predicts review effort for agent PRs from static cues (AUC 0.96 on chronological splits, about 0.83 across repositories); arXiv:2604.03196 reports that, among 3,109 PRs in a commented state, PRs reviewed only by code-review agents merged at 45.20% against 68.37% for human-reviewed ones. These concern review burden and merge outcomes, not evidence of correctness.
**Patents** (read from Google Patents, claims as displayed, not a legal opinion): US11379349B2 (hashes of test environment and results across machines), US10698666B2 (instrumented builds that install missing packages), US12204434B2 (reproducible-build blueprints; no claim on test replay, environment capture or claim verification) and the pending CN120780274A (a knowledge graph with a hash fingerprint of the runtime environment compared against a test baseline to halt deployment, machine-translated claims) overlap with hash-bound evidence, environment fingerprinting and recovery. We therefore present none of these as our contribution; a professional claim-by-claim review is outstanding. The novelty statement in section 1 remains conditional on that review, on unread repositories, and on prior work our searches did not surface. The replay evaluates the agent's target tests; it does not map each natural-language claim to its command.

## 8. Conclusion
When an agent's passing test result is replayed in a clean sandbox, the packages the agent had installed when it ran the tests reproduced 91% of valid results on a random sample of real agent-PR tasks, against 55% when the environment was reconstructed from the repository, with no result reproduced by reconstruction alone (pre-registered, feasibility scale, Python packages only). Agent-declared recipes were the fragile context in the earlier, selected cohorts. The contributions of this feasibility study are the measurement, the record of how a capture design survived a size-guard measurement defect, and a fail-closed open-source replay tool; the multi-context protocol is a design, not a result, since it was not ablated or compared with the tools in section 7. Capture does not show that agent claims are true, only that the agent's environment can be replayed; the boundary of what is demonstrated is Python dependency state, not complete execution state.
