# Can an agent's "the tests pass" be reproduced by someone else? A feasibility measurement on real coding-agent pull requests, and a fail-closed replay instrument

*Working draft, 2026-10-10. Path 1 of `docs/research/forecast_grounding/PAPER_FRAME.md`: a bounded measurement and negative-result paper with an open artifact. Every number below is from this repository's pre-registered studies; post-hoc analyses are labelled. Novelty is stated only as a potential gap requiring further verification (`PRIOR_ART_2026-10-10.md`).*

## Abstract
Coding agents routinely end a task by saying that tests pass. We ask whether an independent party can obtain a determinate verdict on that specific claim for a real change, and what the verifier needs to know. We freeze a pull request's patch and replay its tests in a clean sandbox under several execution contexts: the repository's own declarations, a recipe the agent itself declares, and the agent's exact package list. No language model is in the verdict path; "unknown" is a first-class outcome. On 140 real agent PRs, only 19% reached a usable zero-config run (a property of the tool, not a claim-level rate). On 12 designed tasks with hidden environment state, a self-declared recipe recovered what repository-only replay could not (zero-config 42-50%, recipe 75-83%). On 32 real PRs (Stage B1, feasibility) the repository alone reproduced 97% of passing claims and, with the agent working in a preloaded environment (Stage B2), 96%; agent-declared recipes were the weaker context (46%, about 62% after a post-hoc fix), mostly because agents omit tools and packages they take for granted. All real-repository tasks were selected because repository-only replay already worked, so the study can neither show that recipes help nor that they do not. We report the instrument's failure modes found only on real repositories, and release the tool and data protocol.

## 1. Introduction
An agent's "tests pass" is true under conditions the reader cannot see: installed packages, environment variables, generated files, a pinned interpreter. Prior work measures whether agents can build environments (SetupBench), whether declared dependencies match what executes (Vangala & Malik, 2610.00425), and whether an agent's self-reported capabilities survive hidden probes (ResearchEnvBench). None of these, as far as abstracts and the full-text reads in `PRIOR_ART_2026-10-10.md` show, takes a *specific completion claim on a real merged agent pull request*, freezes the patch, and compares independent replay contexts. That unit of analysis is the only candidate contribution; it is a **potential gap requiring further verification**, not an established novelty.
**Contributions (bounded):** (1) a measurement design for claim-level reproducibility with explicit support basis; (2) a reachability funnel on real agent PRs for a zero-config verifier; (3) a feasibility measurement on real PRs and its selection-limited reading; (4) the instrument's real-repository failure modes; (5) an open-source, fail-closed, deterministic replay tool with an adversarial test suite.

## 2. Instrument
Agentvow extracts claims from an agent's final message, then decides each by deterministic collectors only. Verdicts: CONTRADICTED / SUPPORTED_BY_PRIOR_EVIDENCE / NOT_CONTRADICTED / UNKNOWN; unknown is never converted into confidence. Tests run in a platform sandbox (macOS `sandbox-exec`, Linux bubblewrap) with no credentials and no network after setup. A **recipe** (`agentvow-recipe/1`) is a small declaration written by the agent: `pip install` steps, an optional repository script that may only create files, a pytest/unittest command and plain environment variables. Recipes are validated against a closed vocabulary; replay builds a clean virtualenv from declared steps only. Support obtained this way is labelled `agent_recipe` and says it holds under the agent's declared conditions, not that the repository reproduces it. Guards (found by adversarial review and later by real runs): fail closed when no environment can be built; refuse a setup that installs the project's own name (shadowing); refuse symlinked or file-modifying `prepare`; require the declared command to execute the tests the change added or changed; ignore results when dependency manifests changed; supply the pytest runner when omitted and say so.

## 3. Studies
**D (detection, 140 real PRs, pre-registered).** 70 CI-failed and 70 CI-passed agent PRs from the AIDev corpus. A usable run (the base suite has a passing test) was reached for 27/140 (19%, 95% CI 14-27); missing dependencies dominated the loss. Among 13 usable CI-failed PRs, 2 were declared CONTRADICTED (real regressions, hand-checked) and none was declared fine; one control was a false alert caused by an environment/dependency-version mismatch. *Reading:* reachability is a property of this tool's zero-config ladder and criterion, not a claim-level prevalence; only 26 of 140 PRs contained a real tests-pass claim.
**P (pilot, 12 designed tasks, 36 runs, one model, pre-registered).** Traps with environment state hidden from the repository. Zero-config replay reproduced 42-50% of correct runs; the agent's recipe 75-83%; 19/20 expressible recipes were sufficient. *Reading:* an instrument test showing what a recipe can capture when hidden state exists. The traps were designed around it; this is not a rate.
**A (instrument validity, 24 runs).** Replay determinism held, no validator escapes, recipe replay 23/24 vs zero-config 10/24 on designed tasks.
**B1 (feasibility, 32 real merged agent PRs from 22 repositories, S0-sandboxed Claude Code in an empty virtualenv, one run each, $13.30).** The agent's target tests passed in its own environment in 32/32. Same frozen patch, reproduction: repository-only replay 31/32 (97%, CI 84-99); agent's recipe 24/30 as registered (2 recipes rejected before replay); exact `pip freeze` 31/32. *Reading:* tasks were selected because zero-config replay reproduced the PR's own head tests, so repository-only replay could not fall far below 100% by construction: "the recipe added nothing" is **not testable here**. After fixing instrument faults (post-hoc, 8 non-reproducing runs re-replayed from saved patches): 26/30.
**B2 (ambient, same 32 tasks, agent's virtualenv preloaded with 17 common packages, one scoped command in every context, pre-registered falsification rule, $14.90).** Repository-only 31/32 (96%); recipe (scoped) 15/32 (46%); own command 12/32 (37%); freeze 28/32 (87%). Of 17 recipe non-reproductions, 11 were an omitted `pytest`; after the runner-supplied change (post-hoc re-replay, 10 reconstructable runs): 5 recovered, 3 exposed a second undeclared ambient package, 2 failed uninvestigated; scoped recipe reproduction about 20/32 (62%). *Reading:* the pre-registered reading (repository-only at least 90% means the "small gap" reading survives) held. Agent-declared recipes are fragile when agents rely on tools in their own environment.
**S2 (setup knowledge outside the repository's declarations).** Screening ~300 candidates by deterministic parsing of CI configuration (including tox, make, uv, poetry translations) yielded 2 valid tasks. The CI-parsing route cannot fill the stratum where recipes should matter; prevalence of such situations in the wild is unmeasured.

## 4. Instrument findings (only visible on real repositories)
(1) An honest recipe can be rejected because the vocabulary cannot say it (4/4 generated-fixture recipes in the pilot -> `prepare`; `PYTHONPATH` and `HOME` declarations in 4/64 real recipes, rejected by design with explanations). (2) A declared test command broader than the claim produces false non-reproduction (up to 3/32). (3) `-e dir` flattened to a bare name silently installed an unrelated PyPI package in monorepo replays. (4) On Linux the sandbox hid the DNS resolver config, so sandboxed installs could not resolve hosts. (5) Whole-suite commands, dependency-manifest changes and preinstalled runners each change what a replay means. Each is a way a replay-based verifier can mislead; all were fixed and are tested.

## 5. Threats to validity
Selection: real-repository tasks are conditioned on zero-config replay success; B2 reduces but does not remove the ceiling. One model family (Claude), one run per task, N = 32 (feasibility, no confirmatory inference), 22 repositories, median change 45 lines; reconstruction tasks, not natural bug reports; models may have seen these public repositories. 8 of 32 claims in B1 were the injected sentence "All tests pass." (the target tests are the researchers' set). The replay places `src` and the repository root on the import path, which can make imports succeed that a clean CI checkout would not resolve. Only failing recipes were re-replayed after instrument fixes. Post-hoc analyses are labelled and do not replace the registered tables. The agents in every study were honest (claims true in their own environment, tests not edited): nothing here concerns deceptive agents.

## 7. Conclusion
On real repositories whose setup is declarable, a replay from the repository alone reproduced almost every passing claim, even when the agent worked in a loaded environment; agent-declared recipes are the weaker context unless the verifier supplies what agents take for granted. Whether recipes help where hidden state really exists in real repositories remains untested, and the CI-parsing route to such tasks failed. The artifact (verdict classes, fail-closed replay, red-team suite) is the lasting contribution.
