# Can an agent's "the tests pass" be reproduced by someone else? A feasibility measurement on real coding-agent pull requests, and a fail-closed replay instrument

*Working draft, 2026-10-10. Path 1 of `docs/research/forecast_grounding/PAPER_FRAME.md`: a bounded measurement and negative-result paper with an open artifact. Registered and post-hoc analyses are labelled separately; protocol amendments are listed in `STAGE_B.md` (candidate pool extension, per-repository try cap) and `DETECTION_V2_PREREG.md`. Novelty is stated only as a potential gap requiring further verification (`PRIOR_ART_2026-10-10.md`).*

## Abstract
Coding agents routinely end a task by saying that tests pass. We ask whether an independent party can obtain a determinate verdict on that specific claim for a real change, and what the verifier needs to know. We freeze a pull request's patch and replay its tests in a clean sandbox under several execution contexts: the repository's own declarations, a recipe the agent itself declares, and the agent's exact package list. No language model is in the verdict path (claims are extracted from the agent's final message by deterministic pattern rules or, when none is found, a fixed sentence is substituted (8/32 runs in B1, 13/32 in B2); the recipe is an untrusted proposal); "unknown" is a first-class outcome. On 140 real agent PRs, 11% (15/140) reached a usable run with the registered zero-config ladder, and 19% (27/140) after a sensitivity arm that installs named missing modules (added after 13 rows were seen); both are properties of the tool, not claim-level rates. On 12 designed tasks with hidden environment state, a self-declared recipe recovered what repository-only replay could not (zero-config 42-50%, recipe 75-83%). On 32 real PRs (Stage B1, feasibility) the zero-config ladder (a heuristic built from the repository's own files) reproduced the agent's passing target tests in 31/32 tasks (97%) and, with the agent working in a preloaded environment (Stage B2), again 31/32 (97%); a tests-pass claim was actually made in 24 (B1) and 19 (B2) of those runs, the rest using a fixed sentence. In B2 the agent-declared recipe was the weaker context (registered: 15/32 = 47%; post-hoc, after the verifier supplies the omitted test runner: about 20/32, 63%, from re-replaying only the failing runs, 10 of 11 reconstructable, the 15 passes not re-run; the ladder itself installs pytest, an asymmetry that favours it), largely because agents omit tools and packages they take for granted. All real-repository tasks were selected because repository-only replay already worked, so the study can neither show that recipes help nor that they do not. We report the instrument's failure modes found only on real repositories, and release the tool and data protocol.

## 1. Introduction
An agent's "tests pass" is true under conditions the reader cannot see: installed packages, environment variables, generated files, a pinned interpreter. Prior work measures whether agents can build environments (SetupBench), whether declared dependencies match what executes (Vangala & Malik, 2610.00425), and whether an agent's self-reported capabilities survive hidden probes (ResearchEnvBench); these statements rest on arXiv abstract pages and HTML reads through a summarising fetch tool (`[read-html]`), not yet on PDFs. None of these, as far as abstracts and the full-text reads in `PRIOR_ART_2026-10-10.md` show, takes a *specific completion claim on a real merged agent pull request*, freezes the patch, and compares independent replay contexts (per abstracts and HTML reads that are not yet checked against the PDFs; SetupBench abstract-only; the patents, ProofRun and truth-mcp unreviewed). That unit of analysis is the only candidate contribution, conditional on those unread items; it is a **potential gap requiring further verification**, not an established novelty.
**Contributions (bounded):** (1) a measurement design for claim-level reproducibility with explicit support basis; (2) a reachability funnel on real agent PRs for a zero-config verifier; (3) a feasibility measurement on real PRs and its selection-limited reading; (4) the instrument's real-repository failure modes; (5) an open-source, fail-closed, deterministic replay tool with an adversarial test suite.

## 2. Instrument
Agentvow extracts claims from an agent's final message, then decides each by deterministic collectors only. Verdicts: CONTRADICTED / SUPPORTED_BY_PRIOR_EVIDENCE / NOT_CONTRADICTED / UNKNOWN; unknown is never converted into confidence. Tests run in a platform sandbox (macOS `sandbox-exec`, Linux bubblewrap) with no credentials and no network after setup. A **recipe** (`agentvow-recipe/1`) is a small declaration written by the agent: `pip install` steps, an optional repository script that may only create files, a pytest/unittest command and plain environment variables. Recipes are validated against a closed vocabulary; replay builds a clean virtualenv from declared steps only. Support obtained this way is labelled `agent_recipe` and says it holds under the agent's declared conditions, not that the repository reproduces it. Guards (found by adversarial review and later by real runs): fail closed when no environment can be built; refuse a setup that installs the project's own name (shadowing); refuse symlinked or file-modifying `prepare`; require the declared command to execute the tests the change added or changed; downgrade CONTRADICTED to UNKNOWN when the change edits dependency manifests (post-hoc, in-sample). A leniency added after B2's registered analysis: when the recipe's test command uses pytest and the recipe omits it, the replay installs the runner and says so (the zero-config ladder always installs pytest, so in B2 it had this advantage by construction).

**Zero-config ladder ("repository-only").** A heuristic, not a statement of what the repository declares: `pip install .[test|tests|testing|dev|develop]`, a fixed list of requirements files, dependency groups, plus pytest. Setup steps run with network and unpinned names, so replay depends on live package-index state; determinism was measured only by a same-day twice-replay.

## 3. Studies
**D (detection, 140 real PRs, pre-registered).** 70 CI-failed and 70 CI-passed agent PRs from the AIDev corpus. The registered primary arm (A, the shipped zero-config ladder) reached a usable run (the base suite has a passing test) for 15/140 (11%); arm B, a sensitivity analysis added by Amendment 2 after 13 rows had been seen, retried 83 PRs with the missing modules installed and brought the total to 27/140 (19%, 95% CI 14-27); missing dependencies dominated the loss. Among the 7 usable CI-failed PRs in arm A, 1 was declared CONTRADICTED; among the 13 in the combined set, 2 (real regressions, hand-checked), and none was declared fine (single annotator; 7 of the 11 UNKNOWN were CI failures not reproduced locally); one control was a false alert caused by an environment/dependency-version mismatch (foamlib#453); a guard written after seeing it (post-hoc, in-sample) now downgrades CONTRADICTED to UNKNOWN when the change itself edits dependency manifests; SUPPORTED is not downgraded. *Reading:* reachability is a property of this tool's zero-config ladder and criterion, not a claim-level prevalence; only 26 of 140 PRs contained a real tests-pass claim.
**P (pilot, 12 designed tasks, 36 runs, one model, pre-registered).** Traps with environment state hidden from the repository. Zero-config replay reproduced 42-50% of correct runs; the agent's recipe 75-83%; 19/20 expressible recipes were sufficient. *Reading:* an instrument test showing what a recipe can capture when hidden state exists. The traps were designed around it; this is not a rate.
**A (instrument validity, 24 runs).** Replay determinism held (24/24 twice-identical), the validator rejected 0 of the 24 recipes, so its safety rests on unit and red-team tests, not on this stage; 2 repetitions of the same 12 tasks as the pilot and so not independent of it; recipe replay 23/24 vs zero-config 10/24 on designed tasks.
**B1 (feasibility, 32 real merged agent PRs from 22 repositories, S0-sandboxed Claude Code in an empty virtualenv, one run each, $13.30).** The agent's target tests passed in its own environment in 32/32. Same frozen patch, reproduction: repository-only replay 31/32 (97%, CI 84-99); agent's recipe 24/30 as registered (2 recipes rejected before replay; 24/32 = 75% counting rejected recipes as failures, the denominator used for B2); exact `pip freeze` 31/32. The registered hypothesis H1 (recipe replay reproduces more than repository-only replay) was **not supported** (recipe-only 0 runs, repository-only 7). *Reading:* tasks were selected because zero-config replay reproduced the PR's own head tests, so repository-only replay could not fall far below 100% by construction: H1 is **not testable here** and its non-support reflects that ceiling. After fixing instrument faults (post-hoc, 8 non-reproducing runs re-replayed from saved patches): 26/30.
**B2 (ambient, same 32 tasks, agent's virtualenv preloaded with 17 common packages, one scoped command in every context, pre-registered falsification rule, $14.90).** Zero-config ladder 31/32 (97%); recipe (scoped) 15/32 (47%); own command 12/32 (38%); freeze 28/32 (88%). Of 17 recipe non-reproductions, 11 were an omitted `pytest`; after the runner-supplied change (post-hoc re-replay, 10 reconstructable runs): 5 recovered, 3 exposed a second undeclared ambient package, 2 failed uninvestigated; scoped recipe reproduction about 20/32 (63%). *Reading:* the pre-registered reading (repository-only at least 90% means the "small gap" reading survives) held. Agent-declared recipes are fragile when agents rely on tools in their own environment; supplying the runner closed about half of the re-replayed gap and the rest were undeclared project dependencies or plugins, which the verifier deliberately does not supply. A tests-pass claim was made in 19 of 32 B2 runs.
**S2 (setup knowledge outside the repository's declarations).** Of 246 attempted candidates, 32 were valid tasks and only 2 were S2 (found by the original pip-only CI parser). Extending the CI-to-recipe translator to tox, make, uv and poetry and re-screening 56 of the rejected candidates yielded 0 further tasks (2 of 302 attempts in all; about 440 candidates were never attempted, and screening stopped on a rule chosen after seeing the ~1% yield); and both S2 tasks reproduced from the repository alone in B1, so the S2 label was not stable. The CI-parsing route did not fill the stratum where recipes should matter; prevalence of such situations in the wild is unmeasured.

## 4. Instrument findings (only visible on real repositories)
(1) An honest recipe can be rejected because the vocabulary cannot say it (4/4 generated-fixture recipes in the pilot -> `prepare`; `PYTHONPATH` (haliax, both studies) and `HOME` (B2) declarations in 6 of 63 real-repository recipes written (B1 32, B2 31; the same two haliax tasks appear in both studies), rejected by design with explanations). (2) A declared test command broader than the claim produces false non-reproduction (up to 3/32). (3) `-e dir` flattened to a bare name silently installed an unrelated PyPI package in monorepo replays. (4) On Linux the sandbox hid the DNS resolver config, so sandboxed installs could not resolve hosts. (5) Whole-suite commands, dependency-manifest changes and preinstalled runners each change what a replay means. Each is a way a replay-based verifier can mislead; all were fixed and are tested.

## 5. Threats to validity
Independence: the agent authors the recipe that is replayed, so a hostile agent could declare a conveniently weak one; the sandbox, the differential base/head rule and the support-basis label limit but do not remove this (no deceptive agents were studied). Selection: real-repository tasks are conditioned on zero-config replay success; B2 reduces but does not remove the ceiling. One model family (Claude), one run per task, N = 32 (feasibility, no confirmatory inference), 22 repositories, median change 45 lines; reconstruction tasks, not natural bug reports; models may have seen these public repositories. 8 of 32 claims in B1 and 13 of 32 in B2 were the injected sentence "All tests pass." (the target tests are the researchers' set). The replay places `src` and the repository root on the import path, which can make imports succeed that a clean CI checkout would not resolve. Only failing recipes were re-replayed after instrument fixes (the passing ones were not re-run under the changed instrument). Post-hoc analyses are labelled and do not replace the registered tables. The agents in every study were honest (claims true in their own environment, tests not edited): nothing here concerns deceptive agents.

**Environment synthesis benchmarks.** SetupBench `[read-html]` (93 instances; success by a one-line validation command in a fresh shell; no check of the agent's own completion claim; omitted test tooling such as `tox` is a documented failure) and ResearchEnvBench `[read-html]`; the following details are not in its abstract (44 repositories; stages from static imports to distributed GPU readiness; a hallucination criterion compares the agent's self-reported capabilities with hidden probes; no merged PRs). Our B2 "omitted `pytest`" finding is the same phenomenon in a different setting, and auditing a self-report against an independent probe is established; what differs is the claim (a test result on a frozen merged-PR patch) and the comparison of several replay contexts.
**Dependency reproducibility of generated software.** Vangala & Malik 2610.00425 `[read-html]` (50 tasks, 3 agents, 4 languages, 1,000 runs; declared vs installed vs runtime-traced dependencies; no completion-claim check found in the HTML read, a negative claim about a paper not read in full) and its predecessor 2512.22387 `[snippet]` (300 generated projects, 68.3% run out of the box, 13.5x declared-to-runtime expansion). Their object is a newly generated project and its manifest.
**Receipts for agent claims** `[snippet]`. ProofRun, `mcp-truth-check`, Trial and similar tools bind a completion claim to a *recorded* command run and mark it stale when code changes. Agentvow instead re-executes independently and reports what the replay supports, with a stated basis.

## 7. Conclusion
On real repositories whose setup is declarable, a replay from the repository alone reproduced almost every passing claim, even when the agent worked in a loaded environment; agent-declared recipes are the weaker context, largely because of omitted test runners and other ambient packages (supplying the runner closed about half of the post-hoc re-replayed gap). Whether recipes help where hidden state really exists in real repositories remains untested, and the CI-parsing route to such tasks failed. The artifact (verdict classes, fail-closed replay, red-team suite) is the lasting contribution.
