# Changelog

## 0.4.5 (not yet published)
Two additions to the default policy that ask a person more often, three new kinds of checked statement, and three opt-in environment features that were measured and did not help. Items marked "repository" are not in the wheel.
- **Policy rule `harness_warning`** (default `needs_acknowledgement`): when the replay passed but the change modified an existing test file, added or edited a file that runs when tests start, or changed the test runner's configuration, the result is no longer simply allowed: a named person must acknowledge it (set it to `allow` to keep the old behaviour, or `block`). The receipt records why in a new per-claim field `harness_warning` (`modified_test_file`, `autorun_file`, `test_config`). **A behaviour change for the default policy**: a pull request that edits an existing test file now needs an acknowledgement. A policy file that uses the new key is rejected by older Agentvow versions (unknown key blocks), so pin the gate's `agentvow-version` to the release that has it; receipts from older versions lack the field and are unaffected. When this ships, raise the control plane's minimum tool version (`AGENTVOW_CP_MIN_TOOL_VERSION`) to it so a caller cannot pick an older Agentvow to avoid the rule.
- **Policy rule `description_mismatch`** (default `needs_acknowledgement`): a statement about files or documentation that git's change list disagrees with (for example "updated `x.py`" when `x.py` is not among the changed files) is shown to a person, not blocked. Receipts carry a per-claim `mismatch` flag (older services ignore it); a policy file that uses the new key is rejected by older Agentvow versions, as with `harness_warning`.
- **Three more statements are checked** (design, tests and evaluation: `docs/research/CHECKERS_FILES_DOCS_LINT.md`): which files were changed or left alone (`files_scope`, from git's change list), that documentation was updated (`docs_updated`), and that a named linter is clean (`lint_clean`: `ruff check`, `ruff format`, `black`, `flake8`, run in the test sandbox with the repository read-only; the tool must already be installed and its version is reported; any other tool is UNKNOWN). Extraction is rule-based and conservative: only an explicit verb next to a backticked path counts, so most phrasings are not extracted. A disagreement with git's change list is a mismatch for a person (UNKNOWN with attention, overall REVIEW REQUIRED), not CONTRADICTED: on about 1,300 real agent pull-request descriptions the flagged mismatches were real in 60% to 91% of cases depending on the round, and each round still found a new misreading. Only a linter's own findings are CONTRADICTED. Ambiguous names and git-ignored files give UNKNOWN. Statements of these kinds never amount to support on their own: a message with only those adds an UNKNOWN "no claim about tests or impact" finding.
- **"Lint passes" with no tool named** is resolved from the repository's own `ruff` / `black` / `flake8` / `pre-commit` configuration (read as text) and run; nothing is guessed. UNKNOWN when none is configured, when the change touches another language, or when a pre-commit hook cannot be run. On 371 real statements the runnable share rose from 11% to 24%; the rest are mostly TypeScript, JavaScript and Go changes.
- **Hardened after an adversarial review** of the new checkers: flake8 is refused when the repository configures local plugins (they would run repository code); the linter's raw output is never reported (only `path CODE` pairs for files the run was given); a clean lint result is UNKNOWN with attention when the change edits lint configuration or adds a file-level suppression; paths with `.` or `..` segments are never statements and the disk outside the repository is never probed; a timeout kills the linter's whole process group; the tool is looked up only in absolute PATH entries outside the repository.
- **Opt-in, off by default, measured without a gain** (`--setup auto` environment building, 27 repository runs on the repositories whose replay was inconclusive, no verdict gained): `AGENTVOW_LOCK=1` installs from the repository's lock file (`docs/research/LOCK_FILE_EXPERIMENT.md`), `AGENTVOW_PYVERSION=1` builds with the Python version the repository supports (`PYVERSION_EXPERIMENT.md`), `AGENTVOW_DISCOVER=1` installs sub-projects and requirements files beyond the root (`DISCOVER_EXPERIMENT.md`). The gate's CI-derived environment gave the same outcomes as the zero-config ladder on the same five pull requests (`PACK_EXPERIMENT.md`). For a third-party pull request in a repository whose environment is not plain pip, UNKNOWN stayed the outcome.
- **Impact check: names defined inside module-level `if`/`try`/`with` blocks are part of the API** (found by the audit study: a name moved under `if sys.version_info >= (3, 14):` was reported as removed). The same study measured the check's CONTRADICTED at 4 correct of 9 decisive flags on 40 pull requests (`docs/research/AUDIT_STUDY_RESULTS_STAGE2.md`); under the study's pre-registered rule it should become attention-only, which is a decision for the owner and is not done here.
- Repository (not in the wheel): evaluation scripts and write-ups under `research/` and `docs/research/` (autonomy-policy prior art and retrospective, statement coverage, precision on real descriptions); `ruff` added to CI so the Linux sandbox path of the linter runs there (verified green on ubuntu and macos).

## 0.4.4 (2026-10-26)
Plain-language explanations of every decision, a wider warning when a change could have shaped its own test output, and the control plane service features that arrived with them (notification, policy refresh, an experimental fork path). Items marked "repository" are not in the wheel.
- **Harness warning also for test-runner configuration**: a change to `pytest.ini` or `.coveragerc`, or to pytest/coverage settings in `pyproject.toml`, `setup.cfg`, `tox.ini` (it can deselect a failing test without touching a test file), now downgrades SUPPORTED to NOT_CONTRADICTED with the same wording; ordinary edits of the shared files do not.
- **Check text fixes** (`explain`): a rule the policy sets to block is no longer offered an acknowledgement; only receipts that actually need one are listed (each needs its own comment); the requirements for an acknowledger are stated; a supported result a policy wants confirmed asks for a person.
- Repository (not in the wheel), from the fifth review: the policy refresh is per commit and store-based (no page limit, no stale decision after a concurrent fresh one); a failing notification comment uses none of the hourly allowance and nothing is posted on a closed pull request; only plain user logins are mentioned; `notified` and per-commit policy rows are pruned.
- **Fork pull requests, experimental and opt-in** (repository, not in the wheel): `gate-service-fork.yml` (for `pull_request_target`, only after a maintainer applies the label `agentvow-fork-gate`; its replay job is `gate-service.yml`'s except for the guard) and `AGENTVOW_CP_FORK_WORKFLOWS` in the service (a sha-pinned, separate list accepted only for `pull_request_target` receipts, bound through the pull request, its head commit and the base branch ref). Off unless configured. **Never run on GitHub.** `docs/FORK_PRS.md`.
- **Open pull requests are refreshed when the policy changes** (control plane, not in the wheel): on a push to the default branch the service compares the policy file's content with the one the last published decision used; if it differs it re-evaluates every open pull request that has a receipt (50 at once, the rest by the background loop within minutes), republishes their checks and, where a change now needs an acknowledgement, notifies the acknowledgers. It needs the App subscribed to the **Push** event (new Apps made by `register_app.py` are; an existing App needs the subscription added in its settings, which asks for GitHub's passkey or code); without it nothing breaks, the old behaviour remains (checks refresh on the next receipt). An unreadable policy changes nothing and fails the delivery.
- **Acknowledgement notification** (control plane, not in the wheel): when a change first needs a person's acknowledgement the service comments on the pull request, mentioning the listed acknowledgers (so GitHub notifies them), with the plain explanation and the exact `/agentvow acknowledge <id>` command. Once per commit and set of receipts (a republish, reopen, retry or restart does not repeat it; a new push or receipt does); at most 10 mentions and 20 notifications per repository per hour; a failed comment never breaks the check and is retried; `AGENTVOW_CP_NOTIFY=0` switches it off.
- `agentvow policy evaluate` now also prints the policy's `acknowledgers`; `policy explain` uses them (and says nothing about who when an older result lacks them), and in its local mode does not pretend there is a pull request comment flow (that is the control plane's).
- **Plain-language explanations** (`agentvow/explain.py`, new `agentvow policy explain --result FILE`): what happened, what it means for the merge, what to do, who can acknowledge and with which command, and what a pass does not show, instead of a list of rule names. The control plane's check run uses it (title and summary); both gate workflows' job summary uses it when the installed Agentvow has the command (this release and later) and falls back to the old list otherwise. A test fails when a rule is added without a plain sentence. The acknowledgement replies in pull requests are plain too.
- **Test-harness warning widened**: the NOT_CONTRADICTED downgrade ("a green run does not show the tests still test what they did before") now also applies when a change adds or edits a file that runs automatically when tests start (`conftest.py`, `sitecustomize.py`, `usercustomize.py`, a `.pth` file, a test package's `__init__.py`), not only when it modifies an existing test file. A harness hidden in ordinary source or in an extra test file is still believed without a warning (a pinned, documented limit).
- **Strict `capture_authenticated`** (a real boolean or null) in receipt validation.
- Repository (not in the wheel): the control plane refuses receipts made by an Agentvow older than 0.4.3 (`AGENTVOW_CP_MIN_TOOL_VERSION`); in `gate-service.yml` the service is never optional (an empty `service-url` blocks); the manifest helper writes `webhook_secret` and accepts a missing `--workflow-sha`; the deployment walkthrough was corrected after the fourth review.

## 0.4.3 (2026-10-26)
Provenance and policy: what a capture proves is now stated in every receipt, and the gate workflows were split so that local use needs no credential. The other changes below are in the repository, not in the wheel.
- **Receipt provenance fields** (per claim): `capture_authenticated` (true local capsule, false supplied bundle, null none), `state_binding` (`capsule`, `git_tree`), `partial_replay` (the replay left out pinned packages). New policy key **`partial_capture`** (default `needs_acknowledgement`): a supported result from a replay that left out pinned packages needs a named acknowledgement. A policy file that uses the new key is rejected by older Agentvow versions (unknown key blocks), so pin the gate's `agentvow-version` to 0.4.3 or later when you use it. Receipts without the fields stay valid and old receipts with `dropped_pins` are treated as partial.
- **Gate workflows (not part of the wheel)**: `gate.yml` is now the local-decision workflow (replay, decide; `contents: read` only, no OIDC permission, no service inputs) and the new `gate-service.yml` holds the upload job; their replay jobs are identical (tested). The control plane trusts only `gate-service.yml` and refuses to start unless each trusted workflow is pinned to a full 40-character commit sha; it also requires the token's `job_workflow_sha` to agree. `service-url` is no longer checked in the replay job (the upload job refuses an address that is not in the workflow, before requesting any token).
- Docs: `docs/TRUST_MODEL.md` (what each artifact proves), the policy-authority paragraph in `docs/GATE_WORKFLOW.md`, a status matrix in `docs/CONTROLPLANE_PHASE1.md`, the current capture evidence in `docs/EVIDENCE_AND_LIMITS.md`.

## 0.4.2 (2026-10-23)
Fixes a regression in 0.4.1; nothing else changes.
- **`agentvow receipt` on a check that could not collect**: when the check had no usable base or too little history it reports its commit as `?`; 0.4.0 put that into the receipt and 0.4.1's stricter validation then turned such a receipt into a `block` ("commit and git_tree must be full hexadecimal object ids"). The receipt now records the commit that is checked out (`git rev-parse HEAD`) when the decision's commit is not a full object id. Found by installing 0.4.1 from PyPI into a repository with a single commit; pull requests with a base (the gate's normal case) were not affected.

## 0.4.1 (2026-10-23)
Fixes found by the first run of the control plane against real GitHub (docs/LIVE_TESTING.md) and by two adversarial reviews of it (docs/review/CONTROLPLANE_REVIEW_2026-10-22.md). No new commands.
- **Content hash and `.agentvow/`**: `reality.git_tree_hash` removed everything under `.agentvow/` from the hash, so a repository that commits a file there (the policy was documented at `.agentvow/policy.json`) produced a receipt whose hash never matched the commit's tree, and the control plane refused every receipt. Files the commit tracks under `.agentvow/` are now content like any other; Agentvow's own untracked state there is still excluded. Hashes of repositories that do not track `.agentvow/` files are unchanged.
- **Receipts are validated more strictly**: `commit` and `git_tree` must be full hexadecimal object ids (40 or 64) and `repo` must look like `owner/name`. Receipts made by 0.4.0 in normal use satisfy this.
- **Many claims**: a receipt keeps at most 200 claims; when there are more, the worst (contradicted, then unknown) are kept and one UNKNOWN claim of kind `truncated` is added, so a long pull request still produces an acceptable receipt that cannot read as support.
- **Gate workflow (`.github/workflows/gate.yml`, not part of the wheel; takes effect when callers pin the new tag)**: the OIDC token is requested for the audience `<audience>:<sha256 of the receipt>` and the receipt's hash is passed from the replay job as a job output (a changed file is not sent); `service-url` can only select an address written into the workflow file (`ALLOWED_SERVICE_URLS`, exact match, checked before a token is requested); the default `agentvow-version` is raised on publication.
- **Control plane service** (`controlplane/service/`, source only, not in the wheel, still experimental): see docs/CONTROLPLANE_PHASE1.md and docs/SETUP_GITHUB_APP.md. Run once against real GitHub; fork pull requests untested.

## 0.4.0 (2026-10-22)
Phase 0 of the monetisation plan (docs/strategy/MONETISATION_PLAN_2026-10.md): a portable, content-bound capture, receipts, an open policy engine, a gate workflow, a pilot report, and a MOCK of the paid control plane (not shipped). An adversarial review of this release found two critical gate-workflow problems and several fail-open cases; all are fixed (marked review).
- **Portable capture bundle and key-less verifier**: `capture --export FILE` and `check --from-capture FILE`. The binding is the git tree hash the working tree would have if committed (`reality.git_tree_hash`): no key, no signature, no environment values, nothing written to the repository; pinned clean git configuration so identical files hash the same on any machine (no system/global config, autocrlf, file-mode or global-ignore effects) (review). The verifier recomputes the hash of its own checkout and refuses to replay on any difference. Versions in a bundle must be exact (no wildcards) (review). The result says the capture was supplied and is NOT authenticated; **what a bundle author can still do** is choose the PyPI packages installed for that tree (an sdist build runs code in the sandbox; a hostile test plugin could alter results), so the result is as trustworthy as its maker (review: the earlier text understated this). Checked on 16 rebuilt agent-run states (15 matched the registered result; 47 of 47 injected stale or foreign bundles refused).
- **`agentvow receipt`** (a minimal record bound to the content hash: verdicts, bases, counts, `capture_source` (`""` none, `local`, `bundle`), category names; no source, free text, paths or environment values; optional PR number) and **`agentvow policy evaluate|init`** (an open, deterministic policy engine: allow, block, needs_acknowledgement). A contradiction can never be acknowledged away; acknowledgements count only from a listed person for exactly one receipt. Hardening (review): strict receipt validation (types, sizes) so a malformed receipt blocks instead of crashing; verdicts are normalised and an unrecognised verdict blocks (a lower-case `contradicted` can no longer be acknowledged); a configured changed-line coverage floor no longer passes silently when coverage was not measured; an unauthenticated capture needs acknowledgement by default.
- **`.github/workflows/gate.yml`**, a reusable workflow in three jobs (review: restructured): `replay` (contents: read only; Agentvow from PyPI at an exact version, never from the pull request; every Python step runs `-I` from a neutral directory; policy read from the BASE branch, and blocked when it cannot be read), `upload` (the only job with `id-token: write`; no pull-request code) and `decide` (no permissions; any missing piece counts as block). The review had shown that steps run from the pull request's checkout would import a planted `json.py` or `pip/__main__.py` with the OIDC variables in the environment; a test plants both. Inputs and events are validated. Checked by running its own shell steps against a bare origin, the mock control plane and a mock OIDC endpoint; **the three-job version has not run on GitHub** (an earlier single-job version did, in local-policy mode: docs/LIVE_TESTING.md).
- **`agentvow pilot-report`**: a mechanical evidence report over a directory of receipts (latest receipt per commit; decisions under the policy; verdicts; reproducibility; coverage; what could not be recreated; changes that were not simply allowed; rule-based recommendations; a limits section that claims no outcomes). Receipt text is escaped in the markdown, oversized, malformed, symbolic-link and deeply nested files are skipped and counted (review). `docs/pilot/EXAMPLE_REPORT.md` is synthetic and labelled; `docs/pilot/PAID_PILOT_OFFER.md` is a draft offer.
- **`controlplane/mock_server.py`** (a MOCK, standard library only, not shipped in the wheel, not for production): accepts receipts only from an exactly pinned `job_workflow_ref` with the right audience and event, validates receipts before storing, orders by workflow run (not arrival), constant-time admin comparison, CSV cells safe against formula injection (review). The real service must also add: RS256 OIDC verification, GitHub as the oracle for commit to tree, the base-branch policy read, per-tenant access control (the mock's check and audit endpoints have none), rate limits and storage caps. `docs/CONTROLPLANE_THREAT_MODEL.md`.

## 0.3.1 (2026-10-22)
The GitHub Action can replay the tests, and the foreground evidence pack uses the same repository-files environment as the hook. An adversarial review of this release found two unsandboxed execution routes and several action-hardening gaps; they are fixed (marked review).
- GitHub Action: new opt-in input `run-tests` (default `false`) with `test-timeout` and `artifact-name`: replays the repository's tests in the sandbox on the runner (bubblewrap installed on GitHub-hosted Linux runners), in an environment built from the repository's own files, and adds the evidence pack to the summary and the comment. It runs the pull request's code (installs sandboxed with network; tests sandboxed without), and the pull request writes the test output, so a pack is evidence to weigh, not verification. Hardening (review): the action refuses `run-tests` on events other than `pull_request`, `push` and `workflow_dispatch` (not `pull_request_target`, `workflow_run` or comment events) and for fork pull requests on self-hosted runners; the timeout must be a whole number and is passed as a quoted argument; the AppArmor/bubblewrap setup runs only on GitHub-hosted runners; the artifact name is configurable. Run once on GitHub, on a same-repository pull request on `ubuntu-latest` (docs/LIVE_TESTING.md); not verified on forks or macOS runners.
- Sandbox escape closed (review): every probe of an interpreter that lives in a repository-controlled environment (`import pytest`, `import coverage`, the direct-URL listing) now runs inside the sandbox from an empty directory with `-I -s` and a minimal environment (`runner.probe`). Before, a planted `coverage.py` in the checkout, or a `.pth` file written into the environment by a package install, would have executed unsandboxed with the runner's environment (including the token). Tests plant both and assert nothing runs and no token is visible.
- The environment build has an overall wall-clock budget, `AGENTVOW_BUILD_BUDGET` (default 900 s), besides the per-step timeouts (review).
- `check --evidence-pack` without a capture builds its environment from the repository's own files (as the hook path already did); it fails closed, and does not raise, if that environment cannot be built (review). The pack lists the install steps and the CI environment values (`NAME=value`, truncated) the replay used, notes failed or left-out steps and the files the change touched, in the text, markdown and HTML report; its limits line now says that the output of a test run is written by the code under test.

## 0.3.0 (2026-10-22)
The project-native context, one-command setup and clearer UNKNOWN results. Same limits as 0.2.1 (Python repositories; capture covers Python packages only). An adversarial review of this release found and led to fixes for the items marked (review).
- The evidence pack's project-native context is built from the repository's own files, not only the zero-config ladder: setup files and requirements files, the `pip install` lines (and literal environment values) of the first CI workflow job that runs the tests, Dockerfile `pip install` lines and other requirements files (`agentvow/baseline.py`, no new dependency). The pack lists the steps and environment names used, notes any install step that failed or was left out, and says which of the files it read were changed in this change (review). The `--setup auto` zero-config path for the primary replay is unchanged.
  - Safety of reading untrusted files (review): requirements files that contain index or URL options, VCS or direct-URL requirements, absolute or parent-directory includes, or that are symbolic links are not installed; lines that would install the project's own name (compared the way PEP 503 does, with the name read from pyproject, poetry, setup.cfg or setup.py) are left out, not refused; proxy and certificate environment values from CI are dropped; workflow jobs and steps that only run on another operating system or under `if: false` are skipped; `a && pytest` one-liners are split; flow-style YAML is refused with a note instead of silently dropped; the base project install runs before the extras install so a failing extra cannot leave the project uninstalled; nothing raised while building this environment can escape the hook's background worker.
  - What a replay now installs: PyPI names that the repository's own files and workflow name (as before for requirements files; new for the other files). Installs run in the sandbox, but an sdist build executes code, so treat a replay of an untrusted repository like running its tests.
  - Reader check: `scripts/workflow_reader_check.py` compares the small workflow reader with PyYAML on any directory of workflow files. On 531 public workflow files from 64 repositories: identical 518, different 3 (TobikoData/sqlmesh pr.yaml, dlt-hub/dlt main.yml, microsoft/autogen dotnet-build.yml), not compared 10 (YAML errors or no jobs, or refused as outside the supported subset).
  - On the 22 valid runs of the B6 study the product derives the same setup as the research baseline in 15; in 6 more the only difference is the added base `pip install .` line; in 1 (AGI-Alpha, not among the 18 re-runnable runs of the registered comparison) it differs because the product does not validate the CI test command. Replaying the 5 re-runnable runs whose derivation differs under the product baseline gave the same result as the registered replay in all 5 (1 pass, 4 inconclusive).
- A captured environment no longer fails as a whole when one pinned package cannot be installed on this platform: pip names the package it has no distribution for (for example `pymsalruntime`, which has none for Linux), the replay leaves that pin out, installs the rest, and says so (the pack's context, the finding's text and a next step name the left-out packages). Only captured environments are trimmed this way, at most 8 pins; an agent's own recipe is never altered. Checked on the one real case from the Linux study (cartography#1741): before, the install aborted and pytest exited with a usage error; now 131 of 132 pinned packages install and the 8 target tests pass.
- Fault regression suite (`tests/test_faults.py`, `docs/FAULT_REGRESSION.md`): eight scenarios of known-false and known-true "All tests pass." claims through the real sandboxed check, verdicts and exit codes pinned, including where the tool is deliberately silent (a fault in code no test runs) or unknown (a fault only a new test catches).
- `agentvow init`: adds the two Claude Code hooks (PostToolUse `post-test-hook`, Stop `check --hook --evidence-pack`) to `.claude/settings.local.json` (`--shared`: `.claude/settings.json`; `--user`: `~/.claude/settings.json`). It shows what it will change, asks for confirmation (`--yes`, `--dry-run`), keeps a timestamped backup and the file's permissions, and runs the end-to-end self test. `--remove` deletes only its own hook commands. Hardened after review: it refuses a settings file, folder or temporary file that is a symbolic link; writes through a fresh exclusive temporary file; recognises only real Agentvow commands (not look-alikes); never edits another hook in the same group; leaves an existing Agentvow hook with other flags unchanged unless `--force`, and names it in the preview; the fallback command is `python -I -m agentvow` so a repository cannot shadow the package; the local exclude entry works in worktrees and submodules. Live-checked on Claude Code 2.1.263 through `.claude/settings.local.json` before the hardening; the hardened version is covered by unit tests and a re-run of the live check is listed in docs/LIVE_TESTING.md.
- Actionable UNKNOWN: when a context of the evidence pack did not reproduce, the pack adds a "Next step" for it: the missing package and which context lacked it (and an install step that failed, when one did), a credential the tests need, a size/disk/time guard stop (with `AGENTVOW_MAX_ENV_MB`), a command that ran no tests, a test timeout, a failure, or the project's own package not importable (`agentvow/advice.py`). The wording does not assert a cause the data does not show (review). The project-native context no longer tells the reader to pass `--python`.
- The receipt states what the replay saw beyond the commit: uncommitted changes and new untracked files (copied in), uncommitted symbolic links not copied, and that git-ignored files are not included; a failing test with ignored files present carries a caution.

## 0.2.0 (2026-10-13)
New since 0.1.0: independent replay of agent-declared recipes and of captured environments, changed-line coverage, session audit, and the fixes found by the real-repository studies in `docs/research/forecast_grounding/`. Still not a safety verdict; see `docs/SECURITY_MODEL.md`.
- Capture at claim time: `agentvow capture` records the Python packages of the agent's environment (signed, bound to the exact commit and working tree); `check --from-capsule` and the hook's `--capture --background-tests` replay the tests in a clean environment built from them, with support basis `captured_environment`; fails closed when no capsule matches the state. Based on the Stage B6 result (see docs/CAPSULES.md).
- `--changed-coverage`: with `--run-tests`, the report says how many of the changed executable source lines the tests actually ran, and names the lines and files that no test reached (measured with `coverage` under an empty rc file inside the sandbox; informational, never changes a verdict). Motivated by a post-hoc study where about half of evidence-closed agent patches had changed lines no test ran.
- When a resource guard (size, disk, timeout) stops an environment install, no tests are run in the partial environment; the result says the environment could not be built and why, instead of a misleading "missing dependency".
- The replay environment size guard (default 700 MB) can be raised with `AGENTVOW_MAX_ENV_MB`; found by Stage B5, where it turned heavy but legitimate captured environments into "missing dependency" results (4 of 18 valid runs).
- A recipe that declares `HOME`/`TMPDIR` is still rejected (a redirected HOME could point tools at agent-planted config) but the message now says why and that the replay already supplies an empty, writable HOME and TMPDIR; agent instructions say so. Found by Stage B2: 2 of 32 agents redirected HOME to work around their own sandbox.
- Recipe replay installs `pytest` (the runner only) when the recipe's test command uses it but does not declare it, and states that in the verdict (`meta.runner_supplied`); found by Stage B2, where 11 of 17 failed recipe replays were an omitted runner.
- `--recipe`: claims with preconditions. The agent declares its setup and test command; Agentvow replays only that in a clean sandbox.
- Recipe `prepare` step (run a repository script in the sandbox before the tests); claim extractor accepts singular and suite forms ("The test passes").
- Recipe hardening from a red-team suite (fail-closed environments, tool-config env prefixes, shadowing, symlinked scripts), test-selection guard, default key dir always hidden.
- Recipe replay: monorepo sub-package installs cleaned up with their sources importable per worktree; changed-tests scoping when the declared command runs more than the claim covers; clearer recipe guidance.

- Visual HTML report, markdown summary, JSON; hook for Claude Code and GitHub Copilot (Stop/agentStop) with sealed results; VS Code extension (status bar, notifications, `@agentvow`); GitHub Action; `doctor`; `agent-instructions`.
- Security hardening after three adversarial reviews (sandboxed installs/tests, signed evidence and seals, symlink-safe writes, hardened git).
- Studies and honest limits in `docs/research/`.
